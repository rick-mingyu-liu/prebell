# PreBell runbook

Operational notes for the owner. Plan 1 Task 13 adds the deploy, cron and rerun sections to this file.

## LLM provider

Every LLM call goes through one provider: reason extraction while building facts, and the EN/ZH drafts. The generator Worker picks the provider from config when each queue batch starts. Claude is the primary provider and the default; DeepSeek is the fallback.

| `LLM_PROVIDER` | API | Secret | Default model |
|---|---|---|---|
| `claude` (default) | `https://api.anthropic.com/v1/messages` | `ANTHROPIC_API_KEY` | `claude-sonnet-5-5` |
| `deepseek` (fallback) | `https://api.deepseek.com/chat/completions` | `DEEPSEEK_API_KEY` | `deepseek-flash` |

- `LLM_PROVIDER`, the optional `LLM_MODEL` and `LLM_EFFORT` are plain vars in `crates/generator/wrangler.toml` under `[vars]`. If `LLM_MODEL` is unset or empty, the provider's default model is used. If `LLM_PROVIDER` is unset, it is `claude`.
- DeepSeek requests always send `thinking: {"type": "disabled"}`, so `deepseek-flash` answers without a chain of thought, as the retired `deepseek-chat` did. Another `LLM_MODEL` (for example `deepseek-v4-pro`) also runs without thinking.
- `LLM_EFFORT` (Claude only) sets `output_config.effort` on every request: `low` (default), `medium` or `high`. `none` leaves the field out; use it for a model that does not support effort. Any other value is a config error: see the next point. DeepSeek ignores it.
- The secrets are set only with `wrangler secret put` (production) or in `crates/generator/.dev.vars` (local, git-ignored). They are never committed.
- An unknown `LLM_PROVIDER` or `LLM_EFFORT` is a config error. The premarket and recap jobs then never run, and each one raises one `error` alert per ET day, keyed `config:<job>:<date>`. The alert reads like `premarket: config error: parse error: unknown LLM_EFFORT: hgih (use low, medium, high or none)`. It names the variable and its value, never a key. Fix the var and deploy.
- The number check (`numbers::check`) and quote anchoring run the same way whichever provider is used. Switching provider does not loosen them.

## Claude (default)

### Set up (owner only; this deploys)

1. `cd crates/generator && pnpm exec wrangler secret put ANTHROPIC_API_KEY` and paste the key.
2. In `crates/generator/wrangler.toml`, `LLM_PROVIDER = "claude"` and `LLM_EFFORT = "low"` are already set. To use a different model, add `LLM_MODEL = "<model id>"`, for example `claude-opus-5-5`. If that model does not support effort, also set `LLM_EFFORT = "none"`.
3. Deploy the generator (`pnpm exec wrangler deploy` in `crates/generator`). Vars take effect on deploy.
4. Check the next run (and time it: compare `updated_at` with 08:00 ET): `pnpm exec wrangler d1 execute prebell --remote --command "select run_key,status,attempts,last_error from runs order by updated_at desc limit 3"`.

Claude thinks before answering, so a build (up to 11 extraction calls plus the EN and ZH drafts) may take longer than on DeepSeek. Effort `low` keeps that short. A build older than 15 minutes counts as stale and a second one starts. If the first runs take more than about 10 minutes, tell the developer: a faster `LLM_MODEL` is the option. Raise `LLM_EFFORT` to `medium` or `high` only if draft quality needs it.

### Local dev

Put the key in `crates/generator/.dev.vars`:

```
LLM_PROVIDER=claude
ANTHROPIC_API_KEY=sk-ant-...
```

Values in `.dev.vars` override `[vars]` under `wrangler dev`. Then follow the local steps in `docs/plan-1-notes.md`. A missing key logs `secret ANTHROPIC_API_KEY is not set; provider calls will fail`.

## Fall back to DeepSeek

Use this if Claude is down, the spend limit is reached or the key is revoked, and the run cannot wait.

1. `cd crates/generator && pnpm exec wrangler secret put DEEPSEEK_API_KEY` (skip if it is still set).
2. In `crates/generator/wrangler.toml`, set `LLM_PROVIDER = "deepseek"` and remove `LLM_MODEL` if you set it to a Claude model. `LLM_EFFORT` can stay; DeepSeek ignores it.
3. Deploy the generator (`pnpm exec wrangler deploy` in `crates/generator`).

Both secrets can stay set the whole time. To go back, set `LLM_PROVIDER = "claude"` and deploy.

### What Claude failures look like

Where a failure shows up depends on which call failed.

- **Reason extraction** (the first calls in a build): a failed call is counted (`llm_err=` in the diagnostics line) and writes one line to `wrangler tail`, `llm error: <purpose>: <error>` (see "Why the brief retries" under "Premarket brief and update"); the facts and the brief's `last_error` hold only the count. If every extraction fails — wrong key, rate limit, outage, or refusals — no mover keeps a reason, the required movers section is missing, and `runs.last_error` reads just `movers`. That is the same thing you see when the news has no usable reasons, so read the `llm error:` lines in `pnpm exec wrangler tail` in `crates/generator`. The run stays `pending` and retries every 5 minutes until 09:25 ET, then it is skipped and an error alert is raised.
- **EN draft:** each draft gets two attempts per tick. If both fail, `last_error` reads `en: llm: <error>` and the run retries on later ticks until 09:25 ET as above.
- **ZH draft:** EN still publishes. ZH is stored as `pending` ("中文版稍后推出") and `last_error` reads `zh: llm: <error>`. Later firings retry ZH, hourly after the morning window. A failure at or after 18:00 ET marks ZH `failed` and raises one warn alert.

Every HTTP error of 400 or above also writes one line to `wrangler tail` with the error type and request id, never the key or the body: `claude http <status>: error.type=<type> request_id=<id>`. Quote the `request_id` to Anthropic support.

A note after the JSON is not an error. Models sometimes add text after their answer; until 2026-11-16 that failed the call (`parse error: trailing characters at line 3 column 1`, which cost the IPO news sweep of 2026-11-16 and three judge replies in the mover-insights trial). The reply's first JSON object is now used and a note after it is dropped (a note may hold brackets, quotes and empty braces, but no JSON object of its own), with one line to `wrangler tail`: `<provider> reply: ignored text after the JSON object: <first 80 characters>`. `wrangler tail` only shows live output, so that line is lost unless someone is watching; turning on Workers Logs (`[observability]` in `wrangler.toml`) would keep it, and is the owner's call. The root-cause fix is the API's structured outputs (`output_config.format` with a JSON schema per call, supported by `claude-sonnet-5-5`), which constrains the reply to one object matching the schema (a `refusal` or `max_tokens` stop can still break it; the provider already refuses both before parsing); it needs a schema for every prompt and is not done.

The `<error>` part:

| Error | Meaning |
|---|---|
| `http status 400` | Bad request, or the organization or workspace spend limit was reached (the API returns 400 for both). `wrangler tail` shows `claude http 400: error.type=invalid_request_error request_id=req_...`; the message is not logged, so check the Claude Console usage and spend limit first, then the request (`LLM_MODEL`, `LLM_EFFORT`). If the limit is the cause, raise it or fall back to DeepSeek. |
| `http status 401` | Wrong or missing `ANTHROPIC_API_KEY`. |
| `http status 402` | `billing_error`: a billing or payment problem. Fix it in the Claude Console. |
| `http status 403` | `permission_error`: the key has no access to this model or workspace. Check the key's workspace and the organization's model access in the Claude Console. |
| `http status 404` | `not_found_error`: almost always a bad `LLM_MODEL` id. Fix or remove `LLM_MODEL` and redeploy. |
| `http status 429` | Rate limit. |
| `http status 529` / `5xx` | Anthropic overloaded or unavailable; usually clears on a later tick. |
| `parse error: truncated` | The reply hit `max_tokens` (16000) or the model's context window (`model_context_window_exceeded`). It is never used as partial JSON. |
| `parse error: refusal: <category>` | The model declined the request. Facts are only saved after a successful EN draft, so a refused build leaves nothing in R2 to inspect; tell the developer the date and category. |
| `parse error: more JSON after the reply's object: <snippet>` | Right after its answer (or after an opening fence) the reply held a second JSON object or array, or text that continues the answer (it opens with `,` `]` `}` `:` or a string that completes an object); or a non-empty JSON object appeared anywhere in what followed ("Corrected: {…}"). A second answer written as something other than JSON (`{'a': 2}`, YAML) is not caught and reads as a note. A split, cut or self-corrected reply is refused whole; the snippet is the first 80 characters of what followed. |
| `parse error: too much text after the reply's object: <snippet>` | More than 4 KB followed the answer. A note is short; this is refused unread. |
| `parse error: EOF while parsing …`, `parse error: expected value …` | The reply was cut short or was not JSON. |
| `parse error: stop_reason: <x>` | The turn ended unfinished in some other way. It is never used. |
| `parse error: ...` (other) | The reply was not a JSON object. |

## Premarket brief and update

- **The brief** (`job=premarket`, run `premarket:YYYY-MM-DD`) builds from 08:00 ET on trading days and retries every 5 minutes until 09:25 ET. At 09:25 an unpublished brief is skipped for the day and raises one `error` alert. A Chinese draft that fails after English published keeps retrying (every firing in the window, then hourly) until 18:00 ET.
- **The update** (`job=premarket-update`, run `premarket-update:YYYY-MM-DD`) rebuilds the brief from 08:35 ET, after the 8:30 ET economic releases, and rewrites the same post at the same URL: fresh facts under their own key, `premarket/YYYY-MM-DD-update.json` (the 8:00 facts stay at `premarket/YYYY-MM-DD.json`; the post's `facts_r2_key` says which one the page reads), both translations, the sources, the front page's index line and a new cover at `covers/<slug>-update-<attempt>.svg` (covers are cached for a day, so no key the site may already serve, the 8:00 one or an earlier attempt's, is ever rewritten). `posts.published_at` keeps the 8:00 time and `posts.revised_at` gets the update's; the post page shows "Updated 8:35 AM ET" / "更新于 上午8:35（美东）". The post keeps the base run key: there is never a second post for the day.
- The update writes only when the gate passes and both the EN and the ZH drafts pass the number check. Its facts and cover go to R2 first; then one D1 batch switches the post to them and writes both translations and the sources, so the post flips all at once. A failed batch leaves the post on the 8:00 facts and text, plus an unreferenced `-update.json` in R2, which the next attempt overwrites, and an unreferenced `-update-<attempt>.svg` cover, which stays (each attempt writes its own cover key). Anything less (a failed gate or draft, a failed cover or facts write, a failed batch) leaves the 8:00 brief exactly as it was, cover included; the update run goes back to `pending` with `last_error` (`cover: ...`, or the D1/R2 error) and retries on the next firing.
- If the rewrite landed but the run write after it was lost (a CPU kill or a D1 error), the next firing after the 15-minute lease sees `posts.revised_at` set and marks the run `published` without building again.
- A Chinese retry of the 8:00 brief that drafted from the 8:00 facts writes only while the post's `revised_at` is still the one it read, so it never overwrites the update's Chinese.
- The update never alerts. Read its outcome on the run: `select run_key,status,attempts,last_error from runs where run_key like 'premarket-update:%' order by trading_date desc limit 5`.
  - `published`: the brief was rewritten.
  - `skipped` with `base published after 08:30`: the brief itself went out at or after 08:30 ET and already saw the releases; no build ran.
  - `skipped` with `base not published`: the brief was not out by 09:25 ET (its own skip alert covers that).
  - `skipped` with `published base run has no post` or `base post has no publish time`: the brief's rows are inconsistent (a hand edit?); the update gives up at once instead of retrying all day.
  - `skipped` with any other `last_error` (`zh: ...`, `en: ...`, `movers | ...`, `cover: ...`): no attempt passed by 09:25 ET; the error is the last one. The 8:00 brief stands.
  - Nothing before 08:35 ET, and nothing while the brief is still retrying.
- **Why the brief retries.** The brief publishes only when at least one mover has a verified reason. When none has, the gate finds the required `movers` section missing and the run goes back to `pending` with `last_error` `movers | <diagnostics>` (the diagnostics line: quote counts, `reasons proposed=… kept=…`, `search_err=… llm_err=…`, and so on), and the next firing, 5 minutes later, builds again; at 09:25 ET it is skipped with an alert. On 2026-11-17 this took 9 attempts and the brief went out at 8:41 ET. `llm_err=` counts the failed reason extractions; each failed model call in a build (a mover's reasons, the macro items, the top theme's reasons, a recap's after-hours list) also writes one line to the Worker's log, at most 300 characters:

  `llm error: <purpose>: <error>`

  with `<purpose>` one of `mover <TICKER>`, `macro`, `theme <group>`, `after-hours`, and `<error>` the provider error, for example `http status 529`, `network error: …`, `parse error: truncated`, `parse error: refusal: <category>`, or, for a reply that is not JSON, `parse error: expected value at line 1 column 1; reply began: <first 80 characters>; stop_reason=end_turn` (`parse error: empty reply` when the reply's text was blank, `empty result` when the reply had no text at all; a reply cut off mid-object starts `EOF while parsing` and its first characters show the object). The 80-character start has whitespace collapsed, control, bidirectional and zero-width characters replaced with `?`, and links made inert (`https[:]//…`, a Markdown link's `](` as `] (`), like the note snippet below. No request body, header or key is logged, and the code never logs the prompt; but a reply that repeats its prompt ("Here is the document: …") can put up to 80 characters of it into `reply began`.

  The `reply began` text is part of the provider error itself, so it appears wherever that error does, not only in these lines: a failed draft's `runs.last_error` (`en: llm: parse error: …; reply began: …`), an earnings build's `last_error` and its retry line (`extraction failed: parse error: …`), the insight step's `judge_error` and `writer call failed:` lines, and the IPO news sweep's warn alert to the alert webhook (`IPO watch: the news extraction for <slug> failed: …`). It is at most 80 characters of model text, sanitized as above, so it cannot ping anyone (alerts send no mentions) or carry a live link. A brief's own `last_error` (`movers | <diagnostics>`) holds only the count. Workers Logs are off, so these lines are seen only live: run `cd crates/generator && pnpm exec wrangler tail prebell-generator --format json` across 08:00-08:45 ET and read the `logs` of each `premarket` and `premarket-update` message, beside its `diagnostics:` line.
- **Cost:** one more full premarket build per trading day: up to 12 Tavily searches (8 movers, 3 macro, 1 theme) plus their extractions and the 2-4 draft calls on the LLM. That is about 230 more Tavily searches a month; check the Tavily plan's monthly quota.

## Free plan

The generator runs on the Workers Free plan for now. The limits that matter:

| Limit (Free) | Value | Where it bites |
|---|---|---|
| Cron triggers per account | 5 | `crates/generator/wrangler.toml` uses 2 (a test in `schedule.rs` keeps it at 2). |
| CPU time per invocation | 10 ms | Each queue message is its own invocation (`max_batch_size = 1`). Waiting on the network is not CPU time; JSON parsing and drafting checks are. |
| Fetch subrequests per invocation | 50 | Yahoo, Tavily, the LLM, EDGAR, the alert webhook and (the weekly digest) Buttondown. |
| Subrequests to internal services | 1,000 | D1 and R2 binding calls. The [limits page](https://developers.cloudflare.com/workers/platform/limits/) counts calls to R2, KV and D1 as subrequests and gives Free a separate 1,000 row for internal services, so they are not counted in `subrequests=`. |
| D1 queries per invocation | 50 | The [D1 limits page](https://developers.cloudflare.com/d1/platform/limits/) (1,000 on Workers Paid); a `db.batch()` is one query. The tighter of the two D1 limits, logged as `d1=` (below). The earnings poll and calendar refresh read and write in bulk so their counts do not grow with the watchlist or the number of filings. |
| Queue operations per day | 10,000 | About 1,030 cron messages on a weekday (premarket, premarket update, recap, earnings and cards every 5 minutes) plus earnings builds (at most 3 per poll while filings are open, more after a burst of new ones), at about 3 operations each. |

### Reading `subrequests=`

After each queue message, `pnpm exec wrangler tail` in `crates/generator` shows one line like `subrequests=27 d1=9 job=premarket`: fetch subrequests and D1 queries (each limited to 50 per invocation on Free). Alert delivery logs its own line, `subrequests=N d1=M job=alerts`. Add the two lines to get the invocation's totals. Delivery posts at most 20 alerts, and no more than 45 minus the fetches the job used; the other alerts stay unsent for the next invocation, so a backlog drains 20 per firing. It makes 2 D1 queries however many it posts (the read, and one update marking them all sent), and it is skipped when the job already used more than 48, so an invocation never passes 50. Most firings show `subrequests=0`: the clock decides nothing is due, and only D1 is read.

- A premarket build is: cookie 1, crumb 1, 11 v7 batches, 4 futures, at most 8 mover searches and at most 8 extractions, up to 3 macro searches and 1 extraction, at most 1 theme search and 1 extraction, 2-4 drafts. The facts stage stays at 40 or fewer (`BUDGET_SOFT` is 40); the whole invocation is at most 43, or 44 on the Yahoo 401-refresh path, where the guard drops the theme search to absorb the refresh. "What to watch" adds at most 2 release-page fetches, only once an event's time has passed (in practice the 8:35 update on a jobs or CPI day) and only while they fit under `BUDGET_SOFT`; skipped, the event stays scheduled with its schedule link. Four movers per side is the free-plan budget choice. 150-symbol Yahoo batches, which would bring back five per side, wait for a live check from another network.
- A premarket update build (`job=premarket-update`) is the same as a premarket build, in its own message and so with its own 50.
- A recap build is: 4 index charts, cookie 1, crumb 1, 11 v7 batches, at most 8 mover searches and at most 8 extractions, up to 3 macro searches and 1 extraction, the after-hours search and extraction, at most 1 theme search and 1 extraction (the recap usually has no room for it), 2-4 drafts. The facts stage stays at 40 or fewer with after hours included and the theme search skipped; the whole invocation is at most 43, or 44 on the Yahoo 401-refresh path, where the guard drops the second and third macro queries to absorb the refresh. It also reads which earnings checks were published that day: 1 D1 `posts` query plus 1 R2 facts read per earnings post. Those are internal-service subrequests, so they do not show in `subrequests=`.
- An earnings build (`job=earnings:build`) is: the filing index, the exhibit, up to 5 XBRL concepts, the extraction, then the share move (cookie 1, crumb 1, 1 v7 quote; 6 on the Yahoo 401-refresh path), then 2-4 drafts: 12 for a typical build (4 concepts, 2 drafts), at most 18 (12 before the share move), plus 2 for another filing's Chinese retry in the same invocation (`a_build_stays_under_40_subrequests`). The share move is read only while it fits under `BUDGET_SOFT`, never retried, and is skipped on weekends and holidays.
- An earnings poll (`job=earnings`) is 1-3 requests for EDGAR's current 8-K feed (usually 1: it reads back only to the previous poll), whatever the watchlist's size: the feed lists every company's 8-Ks and the watchlist filter runs in memory. It then reads the current 6-K feed the same way (1-3 requests) and adds each new 6-K that a watched foreign filer filed near its calendar date to a pending list (kv `edgar_6k_pending`); it reads no 6-K itself, so at most 6 requests in all. A feed page whose reply is not a feed is asked for once more in the same poll (see "A feed reply that is not a feed"), so a bad poll is usually 3 requests (2 for the 8-K page, 1 for the 6-K page) and at most 12 (each of the 3 pages of both feeds retried once), well inside the 50, with alert delivery's 20 posts on top. It queues one `earnings:6k` message per pending 6-K, at most 3 a poll. Each `earnings:6k` message (`job=earnings:6k`, on the poll's serial queue) reads one 6-K: the filing index and the first 32 KB of the results document, 2 requests. A build (`job=earnings:build`) is counted in the bullet above: at most 18, 20 with a Chinese retry. The calendar (`job=earnings:calendar`) is the Yahoo cookie, crumb and 12 v7 batches (about 560 symbols, 50 per batch, whatever the seeding window), plus up to 5 announcement searches with an LLM call each: about 24, or 27 on the Yahoo 401-refresh path. Its D1 work is the refresh marker (a read, the attempt and, on a full read, the done mark), one ranged calendar read, one batch write per 100 changed rows, rule 8's read, the announcement candidates' read and 2 kv calls per check: about 17-21 queries. A failed attempt that will be retried stops after the Yahoo read and its reconcile (3-4 queries). Its `changes=` counts rows written: a seed that agrees with the calendar is not rewritten, so a quiet day shows `changes=0`.
- The macro events check (`job=events:check`, on the earnings queue, queued by a poll once per ET day and again for two hours after each event's time) is 3 fetches once a day (the FOMC calendar and the BLS jobs and CPI schedules) plus at most 4 release-page fetches (each reads only the first 48 KB: BLS release pages are over 1 MB, and their opening summary ends near byte 36,100), and 5 D1 queries (the daily marker read and write, one ranged `macro_events` read, one batch write per 50 changed rows, the "loaded" marker the brief reads). A releases-only run (later the same day) is 0-4 fetches and 2-3 queries. Its log line shows `pages: "fomc=ok jobs=ok cpi=ok"` and the ids released, moved or postponed. Parsing the three pages (about 280 KB) and reconciling took 0.3 ms natively on 2026-11-06; Wasm is a few times slower, still far under 10 ms. The premarket brief and the 8:35 update read the day's events for "What to watch": 1 D1 read, 1 earnings-calendar read, at most 2 release-page fetches (only for events already past their time, so the 8:35 update and not the 8:00 brief, and only within `BUDGET_SOFT`) and 1 write when one is released. The fetch that finds a CPI or jobs release also gives its headline figures (`events/figures.rs`, read from the release's opening); a report the poll already marked released that day is read again within the same 2 fetches, since the table stores no figures. Parsing them took under 0.5 ms natively on 2026-11-10 (regex compile included). A page that does not parse leaves the line as "✓ Released" with the link.
- D1 queries (`d1=`), counted in tests: a premarket brief is about 9 (the run, its post, the index line, both translations, the sources), a recap 10 (plus the day's earnings posts). An earnings build is 11, and 17 with another filing's Chinese retry in the same invocation. A poll is about 9 however many filings the feed shows: the macro events marker, the watermark, one ranged calendar read, one batched calendar write (none when every filing is already shown), one check for known filings, one batch inserting new filings with their runs, the watermark write, the open filings with their runs and the calendar marker; the 6-K part adds its watermark, checked and pending reads, one ranged calendar read when a new 6-K is seen, the pending and watermark writes and 2 per name-mismatch alert, so at most about 15. A poll that saw a feed reply that is not a feed adds 2 (one read and one write of the day's counter, kv `sec_feed_stats:<date>`, for both feeds together), plus, when a retry also failed (and was not refused), 1 for the check for the day's `sec-not-feed` alert (2 when both feeds' retries failed) and 1 more the first time each ET day (writing it). A healthy poll adds none. An `earnings:6k` message is at most 7: the backoff, pending and checked reads, the ticker's calendar rows, one calendar write and the two list writes; the alert after a 403/429 adds 2 and the backoff write 1. A D1 error in the 6-K part is logged (`6-K: ...` in the poll's errors) and the rest of the poll still queues its builds, calendar refresh and events check.
- The weekly digest (`job=digest`, on the earnings queue, Friday evenings only, off by default) is 0 fetches as a dry run, 1 in draft mode (one email create) and 2 in scheduled mode (plus the schedule call). It uses about 6 D1 queries: the kv flag, one ranged calendar read, one `macro_events` read and its loaded marker, one posts read, and when the draft is saved one kv write. Gathering and rendering took about 0.7-0.9 ms cold and 0.1 ms warm natively on 2026-11-06 (two emails then, one now) with that week's 19 calendar rows and 15 checks; Wasm is a few times slower, still far under 10 ms. A Friday poll from 18:00 ET adds one kv read (the flag) to see whether to queue it.
- When a run retries, `runs.last_error` ends with `subrequests=N`: the count when the facts were built, before the drafts. Read it with `pnpm exec wrangler d1 execute prebell --remote --command "select run_key,last_error from runs order by updated_at desc limit 3"`.
- Redirect hops count toward the 50 but are not visible here, so treat 45 or more as at the limit. Past 50, fetches fail with a network error, and the build shows them as `net=` or `search_err=` in its diagnostics.

### Reading the diagnostics line

Each build logs one `diagnostics:` line as soon as its facts are built, before the drafts, so the line is there even when a build dies in them; a retrying run stores it in `runs.last_error`. Premarket, recap and earnings builds that get as far as the cover step then log a second, short line, `cover=ok|err|none`. Besides the quote, mover and search counts, these show why news was dropped:

- `hedged=` on the `reasons` part counts mover reasons dropped because `summary_en` hedged its cause ("which could support the gain"). In code the counter is `reasons_hedged`.
- `news_noise=` counts search hits dropped as noise before any LLM call: MarketBeat filing alerts, 13F, holdings and institutional-ownership pages, "trims position"-style titles, analyst consensus-rating alerts ("Has Consensus Price Target of", "Average Rating of"), and Tavily's own company-profile pages (`tavily.com/knowledge/`). Each mover and macro news query asks Tavily for `NEWS_EXTRA_HITS` (2) more hits than it keeps, so stale and noise hits do not use up a mover's slots; after filtering, the prompt still gets at most the usual number of articles. `news_stale=` and `news_noise=` count every dropped hit, including the extra ones.
- `reported=N reported_err=M` (recap only, last part) counts the earnings checks published today that the recap links as already reported. `reported_err=M` above 0 means that many D1 or R2 reads failed; the recap still publishes and lists the checks it could read.
- `macro queries=Q hits=H items=I` (premarket and recap) covers the macro section. `queries=` is how many of the three macro searches ran: 3 normally, fewer when the budget guard dropped the later ones (see "Budget guard" below), and 1 when the first search failed with HTTP 401, 403 or 429 (Tavily auth or quota), since the others would fail the same way. `hits=` is the hits left after merging the searches, dropping duplicates, stale and noise hits, and capping at 8. `items=` is the macro items that passed the quote check and are in the facts, at most 5. `items=0` means the brief has no macro section; with `hits=0` there was nothing fresh to read, with `hits=` above 0 the extraction kept nothing.
- `themes found=N kept=K searched=0|1` (premarket and recap) covers the themes section. `found=` counts the industry groups that qualified as a theme, `kept=` the ones shown after the cap of 3. `searched=1` means the top theme had no reason from its movers' news and its own search ran; `searched=0` means no theme formed, the top theme already had a reason, or the budget guard skipped the search. `found=0` means the brief has no themes section and the front page shows no themes block.
- `cover=ok|err|none` (premarket, recap and earnings builds; its own line after the cover write, once per build that publishes; never in `runs.last_error` or the stored facts) says what happened to the post's cover graphic. `ok`: the SVG was stored in R2 as `covers/<slug>.svg`. `err`: the R2 write failed; the post still publishes and shows the flat tile, and a separate `cover write failed: <error>` line follows with the R2 error (also never in `runs.last_error`). `none`: there was nothing to draw, so the post shows the flat tile. That means no non-zero mover for a brief, fewer than two revenue quarters and fewer than two diluted EPS quarters in the last 8 slots for an earnings check, or a value label that failed the number check.
- `share_move=ok|missing (reason)` (earnings builds whose facts are publishable; its own line before the drafts) says whether the check shows the share move under its filing line. `missing` never holds the check back; the reason is `market closed`, `subrequest budget`, `yahoo: <error>` (a 429, a failed cookie or crumb), `stale: ...` (the quote's own time is not in the session the build runs in, or is before the filing was accepted; or, premarket and after hours, the close the move is measured from came after the filing, as for a report filed during regular trading) or `incomplete quote`.

### Tuning themes

A theme is an industry group from `crates/core/data/universe.txt` whose members move together. The rules are constants in `crates/core/src/themes.rs`:

| Constant | Premarket | Recap |
|---|---|---|
| `min_move`: a member counts at this move or more | 2.0% | 3.0% |
| `min_median`: the counting members' median move | 2.5% | 3.5% |
| `THEME_MIN_MEMBERS`: counting members on one side | 3 | 3 |

A group also needs the counting members to be at least half of its members that moved more than 0.5%, and a group with 3 or more counting members on both sides is no theme. Dual share classes count once. Themes rank by median times members; `THEME_MAX` keeps 3, and each theme lists up to 6 members (`THEME_LIST_MEMBERS`) and "and N more".

To see what nearly qualified, read the stored facts. Each brief's facts object is in the `prebell-facts` R2 bucket at `premarket/YYYY-MM-DD.json` (`premarket/YYYY-MM-DD-update.json` for an updated brief) or `recap/YYYY-MM-DD.json`, and its `theme_candidates` array has one entry for every group with at least two members beyond ±1.5% (`THEME_STAT_MOVE`), up to 15:

```
cd crates/generator
pnpm exec wrangler r2 object get prebell-facts/recap/2026-11-05.json --remote --pipe | jq '.theme_candidates, [.themes[] | {group, median_pct, more}]'
```

Each entry has `group`, `present` (members with a quote), `up` and `down` (members at or beyond +1.5% and −1.5%), and `median_up` / `median_down` (the median move on each side). A group with `down: 2` and `median_down: -4.0` moved hard but missed on member count; a group with `down: 4` and `median_down: -2.2` had the breadth but most likely missed on the median (the theme rules count members at 2.0% or 3.0%, not 1.5%, so the stats are a wider net). After a week of briefs, change the constants if the same near misses keep showing on days the market plainly had that story; the tests in `themes.rs` pin the values, so update them in the same commit.

### Budget guard

The facts stage keeps optional work under `BUDGET_SOFT` (40 fetch subrequests, `crates/core/src/budget.rs`), which leaves room for the drafts and the Yahoo 401-refresh path. Before each optional step the build checks that what it has used plus the step's cost is 40 or less. What goes first, in order: the top theme's search, then the third macro query, then the second. The first macro query, the quotes, the mover searches and the drafts always run; the recap also keeps room for its after-hours search. In the diagnostics the guard shows as `searched=0` with `found=` above 0 and as `macro queries=` below 3. Neither is proof on its own: `searched=0` with `found=` above 0 also happens when the top theme already has a reason from its movers' news, and `macro queries=1` also follows a 401, 403 or 429 on the first macro search (then `search_err=` is above 0). At the nominal premarket usage the theme search fits; at the nominal recap usage it is skipped and all three macro queries run.

### CPU overruns

An invocation over 10 ms of CPU is killed. In `wrangler tail` it shows with outcome `exceededCpu`. If that happens, or if `subrequests=` gets near 50, the fix is Workers Paid ($5/month): 5 minutes of CPU (30 seconds by default) and 10,000 subrequests per invocation. No code change is needed.

## Cover graphics

Each published post's cover background is an SVG chart of its own figures, drawn by the generator in the paper palette and stored in the `prebell-facts` bucket as `covers/<slug>.svg`. A brief draws its biggest movers as bars: up to 4 gainers above up to 4 losers, with a move that rounds to 0.00% skipped. An earnings check draws its revenue series as bars, or its diluted EPS series when revenue has fewer than two quarters in its last 8 slots. It shows the last 8 slots in grey. When the release has a quarterly figure, that bar is this release's quarter, drawn last in ink with its value labelled. Otherwise all bars are grey and no value is labelled. An IPO write-up draws its milestone from its facts bundle (`crates/core/src/cover/ipo.rs`): `range_set` the price range as an ink band with both ends labelled; `range_changed` the previous range in grey above the new one in ink, on one scale (a share-count change alone: the kept range as one ink band, captioned "UNCHANGED"); `priced` the last range as a grey band with an ink marker at the offering price (the price alone when no range is on record); `listed` the offering price, the first open and the first close as bars, the close in ink; `filed` a four-step track (Filed, Price range, Priced, Trading) with the first step filled; `withdrawn` nothing. A milestone missing a figure its graphic needs gets no graphic, and every price drawn must pass the number check against the write-up's facts. There is no AI call, no credentials and no extra subrequest, and nothing in the cover step can fail a post.

- The Workers AI scene path is gone. `CF_ACCOUNT_ID` in `crates/generator/wrangler.toml` is now unused. The `CF_AI_TOKEN` secret is unused too; the owner may delete it with `cd crates/generator && pnpm exec wrangler secret delete CF_AI_TOKEN`. Old `covers/*.png` and `covers/*.jpg` objects in R2 are harmless.
- Whether a cover was drawn shows in the `cover=ok|err|none` line (see "Reading the diagnostics line"); for an IPO write-up, in its `ipo:article` log line: `published <slug> (cover ok|none|err: <error>)`. A post without a graphic shows the flat light tile.
- On the site, the article and front-page lead covers show the tag, both cover lines and the amber bar above the chart. Small covers (list rows and the front page's earnings checks) show the tag and the chart only; a flat tile keeps its lines.
- **Backfill for posts without cover lines:** `scripts/backfill-covers.sh` (repo root) reads the remote D1 and the `prebell-facts` bucket, recomputes each post's cover lines with the `cover-lines` binary, and writes one `UPDATE` per post and language to `backfill-covers.sql` (git-ignored). It never runs the SQL; the owner reviews it and applies it with `cd crates/generator && pnpm exec wrangler d1 execute prebell --remote --file ../../backfill-covers.sql`, and rerunning the script afterwards lists only the rows still missing lines.
- **Backfill for posts without a graphic:** `scripts/backfill-graphics.sh` (repo root) takes every published post whose `cover_key` is empty or not an `.svg`, downloads its stored facts, draws the graphic with the `cover-graphic` binary, uploads it to `prebell-facts` as `covers/<slug>.svg` (this writes to the remote R2 bucket) and writes the matching `UPDATE` statements to `backfill-graphics.sql` (git-ignored, SVGs in `backfill-graphics/`). A post whose facts give no graphic gets `cover_key = NULL`, so its old scene image stops showing under the paper styling and it shows the flat tile; the next run lists it again and writes the same statement. It never runs the SQL; the owner applies it with `cd crates/generator && pnpm exec wrangler d1 execute prebell --remote --file ../../backfill-graphics.sql`. A post whose download, render or upload failed gets no statement and shows up again on the next run.

### Share cards

Link previews (Open Graph and Twitter cards) need a raster image: WeChat, X and Facebook do not show SVG. Every post with an SVG cover gets one, IPO write-ups included. The generator's `cards` job (its own message on the `JOBS` queue) looks at the 30 newest published posts with an SVG cover and a trading date in the last 14 days, and renders the first one without a card: `covers/<stem>.svg` recomposed at 1200×630 under the PreBell nameplate, with the ticker (earnings) and trading date top right (an IPO write-up: "ANTHROPIC IPO · 2026-11-10", the company name from `ipo_watch.name` uppercased when it is printable ASCII and at most 18 characters, else "ANT IPO · …" from `ipo_watch.symbol`, else "IPO · …"), rasterised by resvg to `og/<stem>.png` in `prebell-facts`. Cards carry no headline (the platforms print the page's title beside the image), so one card serves both languages and only Latin fonts are embedded: static cuts of the site's Inter and Newsreader in `crates/core/data/fonts/` (OFL), made by `python3 scripts/build-card-fonts.py` (needs `pip install fonttools brotli`; rerun only if covers gain characters outside printable ASCII). A build that publishes a post with a cover (or the 8:35 rewrite, or an IPO cover backfill) sends a `cards` message as soon as it finishes, so the card normally exists within a minute; its log line then ends `; card queued`. Every cron firing also sends one, which catches anything missed (a failed send, an older post). A post's page names its own card (`og:image`, `twitter:image`, the JSON-LD image) only once R2 has it (one R2 head per page render) and the default card (`apps/web/public/og-default.png`) before that, so a link shared in the first minute caches the default card's URL rather than a card URL that later changes what it shows; posts older than the window keep the default card. `/og/<stem>.png` serves the card, or the default card for 5 minutes while it is missing.

- Its log line is `job cards: card og/<stem>.png (<bytes> bytes)` or `job cards: no card missing`; an R2 or render error is `job cards: <error>`, never an alert, and the next message tries again. A cover that is missing or not a graphic is skipped without rendering.
- **Give-up:** each render first counts an attempt in `og/<stem>.attempts` (R2, never served), so an invocation killed for CPU counts too. After 3 attempts the card is given up and that post keeps the default card; the posts behind it are not held up. The `prebell-jobs` queue's default 3 redeliveries are bounded by the same count. To retry a given-up card, delete its `.attempts` object: `cd crates/generator && pnpm exec wrangler r2 object delete prebell-facts/og/<stem>.attempts --remote`.
- **CPU:** a render is about 3-4 ms warm and up to about 20 ms in a cold isolate (wasm compiled on first use), measured in V8 on the build machine. The Free plan tolerates occasional overruns of its 10 ms and terminates a Worker that hits it consistently; renders are a few per day against about 1,000 messages, and nothing else shares the invocation. Check after a deploy with `pnpm exec wrangler tail prebell-generator --format json` (in `crates/generator`) and look for `"outcome":"exceededCpu"` on `job=cards`; if it shows often, Workers Paid is the fix.
- **Size:** resvg adds about 800 KiB gzipped (1,234 → 2,032 KiB gzip, 6.0 MiB uncompressed) to the generator. Cloudflare's limits page counts only the uncompressed size (64 MiB on both plans; gzip is shown for reference, not a limit). What a bigger wasm can strain is the 1 s startup limit: `pnpm exec wrangler check startup` (in `crates/generator`) measured about 28 ms locally on 2026-11-06.
- Preview a card locally: `cargo run -q -p prebell-core --bin card-png -- <cover.svg> "<kicker>" > card.png`. After changing the nameplate, regenerate the default card: `cargo run -q -p prebell-core --bin card-png -- default > apps/web/public/og-default.png`.

## Web site (`prebell-web`)

The site is the OpenNext Worker in `apps/web` (`wrangler.jsonc`, name `prebell-web`). It reads the same D1 database and R2 bucket as the generator: posts and the `kv` row `index_line` (the masthead's index line) from D1, facts, charts and cover graphics from R2 (`/covers/<slug>.svg` serves the R2 object `covers/<slug>.svg`, under `Content-Security-Policy: sandbox` so an SVG can never run script; older `.png` and `.jpg` keys are served too; any other path there, or a missing object, is a 404).

- `BUTTONDOWN_API_KEY` is the site's one secret: the Buttondown API key behind the weekly-digest signup. The owner sets it with `cd apps/web && pnpm exec wrangler secret put BUTTONDOWN_API_KEY` (it lands on `prebell-web`). Until it is set, no page shows the signup form (home, post pages and About check for the key on every request) and `/api/subscribe` returns 503; the form appears once the key is set, with no redeploy, on pages in both languages (the digest is one English email, and the Chinese form says so). Nothing else on the site depends on it. The generator needs the same key for the digest itself. Set the web key last, after a first draft has been checked ("Weekly digest" → "Switching it on, in order"). The signup checks the `source` page (`home`, `post` or `about`) and sends Buttondown only the address, with no tags: Buttondown creates a missing tag only on a plan with tags (Basic or higher), so tags could make a signup fail on the free plan. Buttondown then sends its own confirmation email. An address that is already subscribed gets "You're already on the list." instead of the confirmation line. A Buttondown failure logs only `buttondown subscribe failed, status <code>`, never the body or the key.
- **Domain `prebell.site`** (registered at Namecheap 2026-11-05). The site's custom domain is in `apps/web/wrangler.jsonc` (`routes`), and `SITE_URL` is `https://prebell.site`. The `--var SITE_URL:...` override on deploy is no longer needed. One-time setup (owner only):
  1. Cloudflare dashboard → Add a domain → `prebell.site` → Free plan. Delete any imported records that point at Namecheap parking.
  2. Namecheap → Domain List → `prebell.site` → Nameservers → Custom DNS: the two nameservers Cloudflare shows. Wait for the zone to show **Active**. This usually takes minutes and can take up to 24 hours.
  3. Deploy the site (step 3 below). The first deploy with the route creates the custom domain and its certificate.
  4. Nothing else for www: the deploy also makes `www.prebell.site` a custom domain, and `next.config.ts` permanently redirects (308) every www URL to the apex.
  5. Check: `curl -sI https://prebell.site/en` returns 200, and `curl -sI https://www.prebell.site/en` returns 308 to `https://prebell.site/en`. Canonical URLs in a page's `<head>` start with `https://prebell.site`.
- **Email on `prebell.site`** works the same way as TermPocket: role addresses on the domain forward to the owner's Gmail. PreBell sends no mail of its own (Buttondown sends the digest), so there is no `noreply@`. The addresses are:
  - `privacy@prebell.site`, named in the privacy policy for data requests.
  - `support@prebell.site`, named in the terms, and the generator's `SEC_CONTACT` (EDGAR User-Agent).

  The DNS is on Cloudflare, so forwarding is Cloudflare Email Routing (free), not Namecheap's. One-time setup (owner only):
  1. Cloudflare → `prebell.site` → Email → Email Routing → Get started. Delete the imported Namecheap `eforward*` MX records and their SPF TXT when asked, and let Email Routing add its own MX and SPF.
  2. Destination addresses: add the owner's Gmail and click the verification link Cloudflare emails to it.
  3. Routing rules: add custom addresses `privacy` and `support`, each sending to that Gmail. Turn on the catch-all only if wanted.
  4. Check: send a message to each address from another account and confirm it arrives.
  Do this before deploying the generator with `SEC_CONTACT = "support@prebell.site"`, so SEC can reach the address.
- **Search and sharing:** every page has Open Graph and Twitter card tags in its language (`shareMetadata` in `src/lib/seo.ts`); posts are `og:type=article` with their card and times, and carry schema.org `NewsArticle` JSON-LD (author Rick Liu, publisher PreBell); an IPO page (`/{locale}/ipo/{slug}`) names its newest write-up's card in that language once it is rendered (one R2 head), else the default card; the home page carries `Organization` and `WebSite`. `/sitemap.xml` lists the fixed pages, every published translation (paired with `xhtml:link` hreflang only when both are published) and the ticker pages that have an earnings check; calendar-only ticker pages and pending Chinese pages are noindex and left out. It is built on a cache miss from two D1 queries (posts, and the tracked IPOs' pages `/{locale}/ipo/{slug}`) and kept an hour in the colo's edge cache through the Cache API (`caches.default`): a Worker's own responses are not cached by their `Cache-Control` header alone, so the pages' `s-maxage=60` does not keep anything at the edge. Building it costs a few ms of CPU per thousand posts (about 16 ms on the build machine at 5,000); past about 2,000 posts, split it into a sitemap index with one file per year to stay inside the Free plan's 10 ms. `/robots.txt` allows everything and names the sitemap; on prebell.site Cloudflare's managed robots.txt (content signals) is prepended to it, which keeps both.
- **Page cache and HTTPS** (`apps/web/worker.ts`, `src/lib/edgecache.ts`). The Worker's entry wraps the OpenNext worker. A plain-HTTP request to `prebell.site` or `www.prebell.site` gets a 308 to HTTPS on the apex (Cloudflare's "Always Use HTTPS" does the same at the edge, if it is ever turned on). A GET or HEAD for a page under `/en` or `/zh` is answered from this colo's edge cache when it can be: only a 200 HTML GET render with a public `s-maxage` and no cookie is stored, for that `s-maxage` (`next.config.ts`: 60 s, posts 300 s); HEAD is answered from a stored page or rendered, never stored. Router (`rsc`, `_rsc`) and server-action requests always render. The key keeps only the query parameters the page reads (`week` on the calendar, `type` and `page` on the archive) and adds the deployed version (`version_metadata` binding `CF_VERSION_METADATA`), so after a deploy no colo serves HTML naming the old build's script and style files. `htmlLimitedBots: /.*/` makes metadata render in `<head>` for every client, so one stored copy fits browsers and bots. Responses say `x-page-cache: hit` or `miss` (check with GET: `curl -s -o /dev/null -D - https://prebell.site/en`). Why: a Worker's own responses are not cached by `Cache-Control` alone, so every view rendered the page again (26 to 334 ms of CPU against the Free plan's 10 ms), and about 300 requests in 15 minutes on 2026-11-18 got 503 "error code: 1102" at one colo. Costs: a post edited in place (the 8:35 update, a revision, a Chinese text published after the English) can show its old state for up to five minutes in a colo that cached it, and a page rendered while R2 failed (no charts or facts, still a 200) stays that way for its TTL in that colo. Nothing purges the cache; entries expire, and a deploy starts fresh keys.

Weeks outside answer 404 before any read, and the end weeks have no link past them; crawlers had followed the old unbounded links back to 2004 and forward to 2050. Weeks more than 8 from today stay `noindex` (`INDEXED_WEEKS`).
- **Cloudflare Web Analytics** (cookie-less). The privacy page says the site uses it, so **set the token in the same deploy that ships that privacy text** (Rick approved the wording on 2026-11-06); a deploy with the text and no token states analytics the site does not run. ### MCP server

`https://prebell.site/mcp` is a read-only [MCP](https://modelcontextprotocol.io) server in the site Worker (`apps/web/src/app/mcp/route.ts`, `src/lib/mcp.ts`, `src/lib/mcptools.ts`; design in `docs/superpowers/specs/2026-11-10-mcp-server-design.md`). It lets a person's own agent read what the site has published. No sign-in, no writes, no live quotes. It ships with the site; there is nothing else to deploy.

- **Tools:** `earnings_calendar` (who reports on which days, up to 21 days and 50 tickers per call, dates from 400 days back to 800 days ahead, with the day's macro events), `earnings_report` (one company's latest check: figures with the press-release sentence each came from, guidance, the share move if recorded, filing and press-release links; or why there is no check), `latest_brief` (the newest premarket brief or recap as a snapshot with its `as_of` time; `is_today: false` and the next due time when today's is not out). Every answer has `lang` `en` or `zh`, a `source` link on prebell.site, its time, and the fixed not-advice / not-real-time sentence.
- **Protocol:** Streamable HTTP, stateless, one JSON response per POST. It answers MCP 2026-07-28 requests (`server/discover`, per-request `_meta`, the `MCP-Protocol-Version` / `Mcp-Method` / `Mcp-Name` headers) and the earlier handshake revisions 2025-11-25, 2025-06-18 and 2025-03-26 (`initialize`, `ping`), which is what most clients still speak. `GET /mcp` shows a short plain-text description for a person; a client asking `GET` for an event stream gets 405.
- **Connect a client.** Claude Code, one line:

  ```bash
  claude mcp add --transport http prebell https://prebell.site/mcp
  ```

  Clients that take a JSON config (Claude Desktop through a connector, Cursor, VS Code and others; the key may be `mcpServers` or `servers`, and `type` may be `http` or `streamable-http` depending on the client):

  ```json
  { "mcpServers": { "prebell": { "type": "http", "url": "https://prebell.site/mcp" } } }
  ```

  To try it by hand: `npx @modelcontextprotocol/inspector --cli https://prebell.site/mcp --transport http --method tools/list`.
- **On the site:** `/en/mcp` and `/zh/mcp` ("For AI agents", linked from the footer and listed in the sitemap) tell a person what the server is and how to connect; `GET /mcp` points there. They follow the off switch below: with `MCP_ENABLED` off the page answers 404 and the footer link disappears within about a minute (pages are edge-cached for 60 seconds); the sitemap is cached for an hour, so its entries can lag by up to an hour.
- **Off switch:** `MCP_ENABLED` in `apps/web/wrangler.jsonc` `vars` is `"true"`. Set it to `"false"` (anything other than `"true"`) and redeploy the site (step 3 above): `/mcp` then answers 404 to everything. Set it back and redeploy to turn it on. A var changed only in the dashboard is dropped by the next `wrangler deploy`, so change the file.
- **Counting calls.** Every POST logs one line without the caller's address: `mcp tool=<name> cache=hit|miss ms=<n>` for a tool call (`cache=miss degraded` when an R2 or D1 failure made a partial answer, which is not cached; for the calendar, `hit` means every week it needed was cached), `mcp tool=<name> error=arguments|internal ...` when it failed, `mcp method=<method> ms=<n>` for the rest (`initialize` is roughly one per client connection), `mcp error=<kind>` for refused requests (`origin`, `too_large`, `parse`, `batch`, ...). Live: `cd apps/web && pnpm exec wrangler tail prebell-web --format pretty | grep '^mcp '` (or `--search "mcp tool="`). `wrangler tail` shows only what happens while it runs. To keep counts for days, Workers Logs has to be switched on for `prebell-web` (an `"observability": { "enabled": true }` block in `wrangler.jsonc` and a redeploy; Free plan: 200,000 log events a day, kept 3 days, shared with the site's other requests). - **What the code limits, and what it does not.**
  - Refused before any D1 or R2 read: a non-canonical host (404), a foreign browser `Origin` (403), a body over 16 KB (413), malformed JSON (400), a JSON-RPC batch (400), and tool arguments that do not check out (a tool result with `isError: true` saying what to fix), among them calendar dates outside 400 days back to 800 days ahead of today (ET), ranges over 21 days, more than 50 tickers. Any unexpected failure is a JSON-RPC `-32603` error, never an HTML 500.
  - The 16 KB cap protects parsing only. OpenNext reads the whole request body into memory before any route runs (for every POST on the site, not only `/mcp`), so a large upload is still buffered, up to Cloudflare's own request limit, before `/mcp` refuses it. A site-wide guard in a custom Worker entry that rejects large POSTs before OpenNext would fix that; it is a follow-up, not in this change.
  - D1 per call: `earnings_report` 1-2 indexed statements; `latest_brief` 1-2 (the newest brief walks `idx_posts_trading_date` backwards and reads a handful of rows, `tests/queryplan.test.ts` guards it); `earnings_calendar` 2 statements per week not already cached (a call touches at most 4 weeks). At most one R2 read per call.
  - Cache (`caches.default`, the colo's Cache API, 60 seconds): `earnings_report` and `latest_brief` answers keyed by their normalized arguments (at most a few keys per ticker, 12 for the brief); the calendar by week and language only, so any ticker subset or range inside cached weeks reads nothing (about 170 weeks a language within the date window). A cached answer still counts as a Worker request; the cache saves D1 and R2 reads, not requests.
- **Rate limit: Rick's decision, in the dashboard.** The code has no per-caller limit. Cloudflare's docs (the rate-limiting binding page, the Workers pricing and limits pages, and the binding's GA changelog of 2025-09-19) never say the Workers rate-limiting binding is included on Workers Free, so it is not used. The zone's Free plan includes exactly **one** WAF rate-limiting rule (match on path only, counted per IP, 10-second period, 10-second block). What such a rule does and does not do:
  - It covers requests to `prebell.site` (and `www`, same zone), not the `workers.dev` address (which `/mcp` no longer answers, but the site's pages still do while `workers_dev` is `true`).
  - It counts per IP, so it slows one address; many addresses together are not stopped, on Free nothing stops them.
  - The site's own pages spend the same quotas: every request to the Worker counts against the 100,000 requests a day, whatever the path, and pages are not cached at the edge, so a loop over `/en` costs as much or more than one over `/mcp`.
  - So whether to spend the one rule on `/mcp` alone or on the whole site is Rick's choice. Either way, add it before or with the first deploy that ships `/mcp`:
  1. Cloudflare dashboard → `prebell.site` → Security → Security rules → Create rule → Rate limiting rules.
  2. Rule name: `MCP per-IP limit` (or `Site per-IP limit`).
  3. When incoming requests match: for `/mcp` only, Field `URI Path`, Operator `equals`, Value `/mcp` (expression `(http.request.uri.path eq "/mcp")`, which also matches `/mcp?…`); for the whole site, a `URI Path` condition that matches every path (for example "starts with" `/`, if the Free plan's editor offers that operator; I could not check the dashboard).

  6. Then take action: `Block`. Duration: `10 seconds`.
  7. Deploy. Check (for `/mcp`): `for i in $(seq 1 20); do curl -s -o /dev/null -w '%{http_code} ' -X POST https://prebell.site/mcp -d '{}'; done` shows 400s (malformed request) then 429s.

The ✓ goes on the release's dateline (the first date from a week before the 6-K to the day after it that comes before the statement or next to a dateline mark such as "–" or "(GLOBE NEWSWIRE)"; a stated period end never counts), else the 6-K's date when that is after the calendar's, and a calendar date that differs is moved, as the 8-K path does. The poll log shows `6-K pages N, read N, reported [..], rejected [..]`; a rejected 6-K is listed with its reason and is not read again (the last 300 read accessions are kept in kv `edgar_6k_checked`; a 6-K with no readable document too; a 6-K whose ticker was reported meanwhile is dropped unread; a 404/410 is retried once by a later message; a 403/429 leaves it pending, raises the once-a-day `sec-throttled` alert and holds every `earnings:6k` message back for 15 minutes (kv `edgar_6k_backoff`; a held message logs `held: true` and fetches nothing); and network errors and 5xx retry up to 5 times; a pending 6-K older than the window is dropped). A foreign row whose CIK files under another name raises the same once-a-day `watchlist-cik:<ticker>` alert as the 8-K path. Coverage is partial: of a review corpus of 49 real 6-Ks from 23 foreign filers, 15 of 17 results releases were recognised (Ryanair's "H1 PAT" release and Barclays' SEC-format excerpt were not) and none of the 32 notices and other filings was taken; a missed release leaves the date Unconfirmed. After the first deploy, check `cpuTime` for `job=earnings` and `job=earnings:6k` lines in `wrangler tail`. Known gaps, left for later: a tag with an unclosed quote (`<td style="x>`) hides the rest of that document from the check (a miss, never a wrong ✓); and past 50 pending 6-Ks the oldest are dropped first (the 8-day age limit and 3 reads a poll keep the list far shorter). Only `full` companies are checked against company announcements (the 5 daily Tavily searches). A poll with no new filing sends one build per open filing that has something due (a build, a retry past its 5-minute pause, a Chinese draft to retry, or a failed run to close), at most 3, and none while a build holds its 15-minute lease. Builds still run one at a time (1-5 minutes each), so the 3 are an upper bound per firing, not the throughput.
- On the first deploy, check one detected filing's time: compare `earnings_filings.accepted_at` (UTC) with the "Accepted" time on its `-index.htm` page (ET). They should differ by exactly the ET offset (4 h EDT, 5 h EST). The feed's time was checked once against an index page before the merge.
- **Retries:** a run whose required data is missing retries every 5 minutes until 6 hours after acceptance, or 1 hour after detection if that is later, and never gives up before its third build, so a backlog cannot fail a filing on its first try. A press release over 2 MB (filings styled inline, such as Duke's and Simon's) is read up to its first 2 MB instead of failing.
- `SEC_CONTACT` must be a real contact email: SEC blocks anonymous clients. With the placeholder, every earnings step is a config error with one `error` alert per ET day, keyed `config:earnings:<date>`.
- SEC answering 403/429 stops that poll and raises one `error` alert per ET day (`sec-throttled:<date>`); the next firing tries again.
- **A feed reply that is not a feed.** When EDGAR answers a current-filings feed request (8-K or 6-K) with status 200 but a body that is not an Atom feed, the poll asks for that same page once more, at once (EDGAR's client waits its usual 125 ms between requests; there is no longer pause), and only for this error: a 403/429 stops the poll as before, and any other error is not retried. At most one retry per feed page per poll. On 2026-11-19 at 11:06 ET the logged reply was EDGAR's own HTML listing page, `title "Latest EDGAR Filings"`, 3292 bytes, answered to the Atom request; that day 3 of 4 polls failed this way for about three hours, before the retry existed (Rick's decision, `docs/decisions.md`, 2026-11-19).

  What the poll's log (`wrangler tail`, the `earnings` message) shows, for each outcome:
  - **The retry is a feed:** the poll carries on as if the first reply had been good (entries, watermark, follow-ups), and logs one line with the first reply's facts. It never contains "not an Atom feed", so searching the log for that text finds only reads that failed (the day's counter is the better count):

    `earnings poll: current filings page 0: retry ok after a non-feed reply (status 200, content-type "text/html; charset=utf-8", 3292 bytes, title "Latest EDGAR Filings", body began: <!DOCTYPE HTML PUBLIC "-//W3C//DTD HTML …)`

  - **The retry is not a feed either:** the poll goes on as after any feed error (that feed's reading stops, it is not throttled, the 6-K feed is still read, the watermark stays put and the next firing, 5 minutes later, reads the feed again), with the retry's facts:

    `earnings poll: current filings page 0, retried once: parse error: not an Atom feed (status 200, …)`

  - **The retry fails some other way:** two lines, the first reply (`current filings page 0: parse error: not an Atom feed (…)`) and then the retry's error (`current filings page 0, retried once: http status 504`). A 403/429 here is a throttle: the poll stops and raises `sec-throttled` as before, its text ending in `current filings page 0, retried once: http status 429`. Any other error stops that feed as it always did.

  (`current 6-K filings page 0…` for the 6-K feed.) The first example's facts are the 11:06 reply's as logged; the others are made from test bodies, not real SEC replies. How to read the facts:
  - The status is always 200 here, since any other status is reported as `http status <code>` before the body is looked at.
  - `content-type "…"` is the header, at most 60 characters; `no content-type` means it was missing. Its own `"` and `)` are printed as `'` and `]`, so it cannot close its quote or the parentheses and pass for the rest of the line (the title gets the same treatment).
  - The length is the body's size in bytes.
  - `title "…"` is the text between the first `<title…>` and the `</title` after it, both within the first 4096 bytes, found by a plain case-insensitive search (entities stay as written, nothing is parsed), at most 80 characters. It is missing when the page has no title there (none, unclosed, or past 4096 bytes).
  - `body began` is the body's first 40 characters after a title, else its first 80. Only the first 512 bytes are looked at. An empty body has none.
  - The title, `body began` and Content-Type are sanitized like a model reply's `reply began` (see "Why the brief retries"): whitespace collapsed, control, bidirectional and zero-width characters replaced with `?`, and links made inert (`https[:]//…`, a Markdown link's `](` as `] (`), with `…` where each was cut.
  - The text in the parentheses is at most 179 characters, cut at its end (so `body began` goes first, then the title), which keeps the log lines at or under 268 characters (256 after a retry that worked) and the stored alert at or under 300. The 11:06 reply's text is about 150 characters and is not cut.

  To read it: a title like a rate-limit or maintenance notice is SEC refusing or down, "Latest EDGAR Filings" is EDGAR's HTML listing page served in place of the feed, `application/json` is an API error, and `0 bytes` is an empty reply. A reply cut off after the feed began is not this error: it parses, with fewer entries.

  **The alert** means "still failing after one retry" (the lead's ruling, `docs/decisions.md`, 2026-11-19). The first poll of the ET day whose retry failed, from either feed and not by a 403/429, raises one `error` alert, `sec-not-feed:<date>`. Its stored message (at most 300 characters) is `SEC EDGAR sent a non-feed reply, retry failed: ` and the retry's error line. When the retry failed some other way (a 504, a network error), the line also carries the first reply's facts, so the day's one alert never describes only the 504: `SEC EDGAR sent a non-feed reply, retry failed: current filings page 0, retried once: http status 504; first reply: not an Atom feed (status 200, content-type "text/html; charset=utf-8", 3292 bytes, title "Latest EDGAR Filings", body began: …)`. The retry's error is cut to 60 characters, then the facts at their end (the body's start first, then the title), so status, Content-Type and length always stay and the message is never over 300. It reaches the alert webhook (Discord, no mentions) with `error: sec-not-feed:<date>: ` in front, so the posted message is at most 332 characters; for example (a test body) `error: sec-not-feed:2026-11-19: SEC EDGAR sent a non-feed reply, retry failed: current filings page 0, retried once: parse error: not an Atom feed (status 200, content-type "text/html; charset=utf-8", 3292 bytes, title "Latest EDGAR Filings", body began: …)`. A retry that works raises nothing, and later failed retries that day log their lines with no alert. A D1 error while checking for or writing the alert never fails the poll: it logs `earnings poll: sec-not-feed alert failed: <error>` and the poll queues its follow-ups as usual. `sec-throttled` is unchanged.

  **The day's count.** Every poll that saw a non-feed reply adds to kv `sec_feed_stats:<ET date>`, JSON counted per feed page read: `non_feed` (first replies that were not a feed, each retried once), `retry_ok` (retries that returned a feed), `retry_failed` (retries that did not: not a feed again, refused, or another error), and `last_at` (the last such poll, UTC). A poll whose feeds were fine writes nothing. A failure to read or write it logs `earnings poll: sec_feed_stats: write failed: <error>` and never fails the poll; a value that does not parse starts the day again. Read it with `cd crates/generator && pnpm exec wrangler d1 execute prebell --remote --command "select key, value, updated_at from kv where key like 'sec_feed_stats:%' order by key desc limit 7"`. `retry_ok` close to `non_feed` means the retry is doing its job; a large `retry_failed` means the feed stays wrong for longer than one request, and the retry is not enough.
- **`empty result` from a filing index or document.** A filing index with no document rows, or a press release or 6-K document with no text, now says what came back: `filing index: empty result (status 200, content-type "text/html", 1543 bytes)` in an earnings build's `last_error` and retry line (for example `missing revenue, eps (revenue: filing index: empty result (…))`), and `exhibit: empty result (…)` for the exhibit. For a press release (read up to 2 MB), a 6-K document or an IPO cover (each read up to its cap) the length is the bytes kept, not the document's full size. A 6-K whose index or document reads this way is still treated as having no readable document (not read again); a build still retries as before.
- **What Yahoo seeds.** Each symbol's date is the later of `earningsTimestamp` and `earningsTimestampStart`: until Yahoo rolls it forward, `earningsTimestamp` is the last report while the start of the range is already the next one, usually an estimate (`isEarningsDateEstimate`). On 2026-11-06 that was 202 of 561 symbols (TCOM, PDD, VIPS, CPRT, WSM among them); reading `earningsTimestamp` first had dropped them all as past. Dates are kept for the next 15 trading days (`SEED_DAYS`; through Fri Nov 27 from Fri Nov 6): 79 seeds that day, against 52 with the old rule and 10 days. An estimate is stored like any Yahoo date (`unconfirmed`, a dashed card) and moves with Yahoo's next guess, but it never quarantines a confirmed date (rule 4), and a quarantined row whose ticker Yahoo now only estimates is confirmed (rule 8). A Yahoo row without a time (`time_slot` `unknown`) counts as an estimate, since every estimate gets `unknown` and every firm Yahoo date on 2026-11-06 sat at 08:30 or 16:00 ET: a company announcement with another date replaces it and is confirmed, with no quarantine or alert (rule 3); a timed Yahoo row that disagrees is still quarantined. An estimate within 21 days after the last report is that report again (CF on 2026-11-06: reported Nov 4, "estimated" Nov 5), so it is not seeded. A ticker Yahoo has no future date for gets no row: compared with AlphaLab's calendar for Nov 9-27, every watchlist company it listed had a Yahoo date, so no second source is read.
- **Calendar retries.** A Yahoo read that misses tickers (a 429, a 401 after the crumb refresh, a network error) is tried again 2 hours later, at most 3 attempts per ET day (`REFRESH_ATTEMPTS`, `RETRY_HOURS`), while the 06:00-22:00 window lasts; an attempt whose retry would fall after 22:00 is the last. kv `calendar_refreshed_on` holds the state: `2026-11-10` once the day is done (a full read, or the last attempt whatever its result), `2026-11-10 1 2026-11-10T12:01:00Z` while attempt 1 waits for its retry. The attempt is written before Yahoo is read, so a dying invocation still counts, and the polls in between queue nothing. The `earnings calendar not refreshed on <date> (N attempts)` alert is raised once, by the last attempt, when it read nothing; the company-announcement checks also wait for the attempt that ends the day, so they stay at 5 a day. The log line shows `attempt: N` and `retry: true` on an attempt that will be retried. Yahoo sees at most 3 × 14 requests a day, each attempt stopping at its first 429. To force a refresh the same day, delete the kv row (`DELETE FROM kv WHERE key = 'calendar_refreshed_on'`); the next poll queues it.
- `EARNINGS_CALENDAR_SEED = "off"` stops reading Yahoo for calendar dates (for example while Yahoo throttles; a 429 shows as `yahoo_429=N` in the `job=earnings:calendar` log line). Company announcements and EDGAR filings still update the calendar.
- **A `watchlist-cik:<ticker>` alert** means EDGAR filed under that row's CIK with a name that is not the row's SEC name (column 6). The filing is skipped. Usually the company renamed itself: regenerate the watchlist with fresh SEC data, `node scripts/build-watchlist.mjs --refresh`, check that column 6 now shows the new name, run the tests and deploy the generator. **Off until the owner turns it on.** Each Friday evening the generator saves next week's digest as a Buttondown draft: one English email to every subscriber (Rick, 2026-11-10: "just english"), which Rick reviews and sends. It works on Buttondown's free plan (no tags, no audience filter). What the email holds is in `docs/spec.md` (goal 6). All its wording is in `crates/core/src/digest/copy.rs`. Edit it there, then run `cargo test -p prebell-core` (`the_fixture_week_renders_exactly` holds the whole email for a fixture week, so update it in the same commit).

### Switching it on, in order

The generator goes first and the signup form last, so nobody signs up before one real draft has been checked.

1. A Buttondown account at buttondown.com (free up to 100 subscribers). In its settings, set the newsletter's sender ("From") name to `Rick`. It is a newsletter setting (`from_name`); no email carries its own. Check the reply-to address too: replies to the digest's question go there (by default the account email).
2. Settings → API: copy the API key. Paste it only into the `wrangler secret put` prompts below, never into a file, chat or commit.
3. The digest on the generator (`prebell-generator`): `cd crates/generator && pnpm exec wrangler secret put BUTTONDOWN_API_KEY`. `DIGEST_ENABLED = "true"` is already in `crates/generator/wrangler.toml` `[vars]` (committed 2026-11-10 at Rick's request), so then deploy the generator.
4. On the first Friday evening after that, open the draft in Buttondown and use its preview, while there are still no subscribers:
   - it is a draft (not scheduled or sending);
   - it renders as plain paragraphs, headings and lists, with every link going to the right page;
   - titles with special characters (`&`, `<`, `*`, `_`, brackets, a `{`) look right. The email is Markdown with backslash escapes and `&#123;` for `{`, and the preview is the only check of how Buttondown's Markdown mode renders them.
   If anything is wrong, switch the digest off (below) and report it.
5. Only then the signup on the site (`prebell-web`): `cd apps/web && pnpm exec wrangler secret put BUTTONDOWN_API_KEY` (the same key). The form appears at once, with no deploy, on the home, post and About pages in both languages.

From then on, the first earnings poll from 18:00 ET each Friday, after that day's calendar refresh has finished (a failed Yahoo read waits for its retry), queues one `digest` message on `prebell-earnings`. Polls queue it again every 5 minutes until 22:00 ET until it is saved. From 21:45 ET the poll queues it even if the refresh has not finished, so a retry that would fall after the last poll never skips the week (see the `digest-stale` alert below).

**Sent emails are public by default.** Buttondown's `archival_mode` defaults to `enabled`, so each digest Rick sends also appears in the newsletter's public web archive. Turn the archive off in Buttondown's settings (or per email) if that is not wanted.

### What Rick sees each week

- A draft in Buttondown's Emails list, Friday evening ET, subject "Week ahead: Nov 9–13" (next Monday to Friday). Its audience is every subscriber. Read it, edit it if needed, and press send (Sunday about 6 PM ET is the plan, or whenever).
- The generator logs `job digest: 2026-11-09 (draft): draft <email id>`, and kv `digest_built_for` holds next Monday's date, so later polls do nothing that week (`2026-11-09: already built`).
- A failure (a wrong key gives `http 401`, Buttondown down gives `http 5xx` or `network error`) logs `job digest: 2026-11-09 (draft): failed: <reason>` and raises one `error` alert per ET day keyed `digest:<date>`. The next poll retries with the same idempotency key (`prebell-digest-<Monday>`), so a retry does not make a second draft. Only `digest: buttondown <call> status <code>` is logged, never a body or the key. A D1 error logs `2026-11-09: store error, left for the next poll: <error>` and alerts under the same key; it is not a config error.
- **`digest-missed:<date>`** (error, at most once a week): a run from 21:55 ET, the last poll, saved no draft: "no draft for the week of 2026-11-09: <why>; nothing retries until next Friday". The reason is the last failure, a store error, or a dry run (the flag on without the generator's key). There is no digest that week unless Rick writes one by hand. It never fires when the digest is off or the draft is saved.
- **`digest-stale:<date>`** (warn): the Friday calendar refresh had not finished by 21:45 ET (a failed Yahoo read was still waiting for its retry), so the draft was built from the calendar as it stood. The log says `(draft, calendar refresh unfinished)`. Check the week's dates against the site's calendar before sending.
- **`digest-not-draft:<date>`** (error, its own key, so an earlier failure alert never hides it): Buttondown answered with a status other than `draft` ("Buttondown answered with <status>, not draft, for email <id>; check it in Buttondown now"). The week is marked done and nothing is scheduled. Look at the email in Buttondown at once.
- A `digest` message on any other day, or before 18:00 ET on Friday, does nothing (`not due (Fridays from 18:00 ET only); skipped`).

### Switches (`crates/generator/wrangler.toml`, `[vars]`)

- `DIGEST_ENABLED`: off unless it is exactly `"true"`, with no spaces or newline around it. Unset, `"false"`, `" true"` or any other value means polls never queue a `digest` message, and a stray one logs `job digest: disabled (DIGEST_ENABLED is not true); skipped`. Setting `BUTTONDOWN_API_KEY` alone does not turn it on.
- `DIGEST_ENABLED = "true"` without the generator's `BUTTONDOWN_API_KEY` secret is a dry run: it gathers next week, renders the email and logs `job digest: 2026-11-09 (draft): dry run, no sender: "Week ahead: Nov 9–13" (3 picks, <n> bytes); BUTTONDOWN_API_KEY is not set`. It sends nothing and writes nothing, so it runs on every poll until 22:00 ET, and the run from 21:55 ET alerts `digest-missed` once.
- `DIGEST_MODE`: `"draft"` (the default: Rick sends) or `"scheduled"`, which schedules the draft for Sunday 18:00 America/New_York (23:00Z under EST, 22:00Z under EDT, using that Sunday's own offset) once Buttondown confirms it is a draft. Any other `DIGEST_MODE` is a config error: one `error` alert per ET day keyed `config:digest:<date>`, which names the variable and value. Leave it on `"draft"` until Rick asks for automatic sending.

### Known gap: D1 queries and the 50 subrequests

Cloudflare's Workers limits page (https://developers.cloudflare.com/workers/platform/limits/, read 2026-11-17) says "A subrequest is any request a Worker makes using the Fetch API or to Cloudflare services like R2, KV, or D1", and also lists "Subrequests to internal services | 1,000" without saying how the two relate. The generator's alert budget (`alerts::delivery_budget`) counts fetches (and, for the insight step, its R2 calls and queue sends) against 50 and D1 queries against a separate 50, as it did before mover insights. If D1 queries count toward the same 50, an insight write message (28 calls, 5 of them D1), alert delivery's 2 D1 queries and up to 20 webhook posts could reach 50. Not changed yet; noted here until a measurement or Cloudflare settles it.

### Rolling back past the rewrite (2026-11-19)

Generator code from before the rewrite does not know the `refused` and `rewritten` stages: it skips such a record as unreadable (named in each tick's log line; it blocks no other bundle and alerts nothing), so that record is never finished and its passing lines are never judged. And when it finishes a record that was rewritten earlier (at `written` or `judged`), it drops `rewritten_from` and the `rewrite_*` fields from what it writes back, so the record loses the writer's refused line and the review page keys the rewritten line as a writer line. So roll back only when no record is at `refused` or `rewritten`. Records are picked up for today and the previous trading day; check each of their keys (in `crates/generator`):

```sh
for d in <today> <previous trading day>; do
  for k in premarket/$d premarket/$d-update recap/$d; do
    printf '%s ' "$k"
    pnpm exec wrangler r2 object get "prebell-facts/insights/$k.json" --remote --pipe 2>/dev/null \
      | grep -o '"stage":"[a-z]*"' || echo "(no record)"
  done
done
```

Any `"stage":"refused"` or `"stage":"rewritten"`: wait for the next message (a record at either stage is a minute or two from `written`), or for the sweep, and check again.

### Switching it off

- The digest: delete `DIGEST_ENABLED` from `[vars]` (or set it to anything but `"true"`), commit, and deploy the generator. Drafts already saved stay in Buttondown until deleted there; a schedule already set stays until unscheduled there.
- The signup: `cd apps/web && pnpm exec wrangler secret delete BUTTONDOWN_API_KEY`; the form disappears and `/api/subscribe` returns 503. Subscribers stay in Buttondown.

## IPO watch

Big upcoming US listings on the market calendar and a page each (`/en/ipo/<slug>`, `/zh/ipo/<slug>`). Design `docs/superpowers/specs/2026-11-11-ipo-watch-design.md`; what the site reads, `docs/superpowers/specs/2026-11-11-ipo-watch-contract.md`; the rules, `docs/decisions.md` (2026-11-11, including the review fixes). Code in `crates/core/src/ipo/`.

### Add or remove an IPO

1. Find the company's CIK on EDGAR (company search; Anthropic is 2130357).
2. Add one tab-separated line to `crates/core/data/ipo-watch.tsv`: slug (the page URL: lowercase letters, digits, `-`), CIK, display name, Chinese name or `-`, aliases or `-`, a note. Aliases are other names news quotes use for the company, comma-separated: a news item is kept only when its quote names the company by its name or an alias. At most 10 lines.
3. `cargo test -p prebell-core` (it checks the file parses), commit, deploy the generator.

The next hourly check reads the company's EDGAR submissions, adds its filings to the timeline, reads the newest registration statement's cover and creates its row; the next day's sweep adds news. Removing a line stops checks and sweeps; its rows stay in D1 and its page keeps showing them. To take a page down, delete its rows by hand (`DELETE FROM ipo_watch WHERE slug = '<slug>'`, and the same for `ipo_filings`, `ipo_facts`, `ipo_items`, `ipo_trading`).

### What runs, and when

- **`ipo:check`** (earnings queue, serial with the polls): queued by an earnings poll at most once an hour (kv `ipo_checked_at`), 06:00-22:00 ET on trading days. One EDGAR submissions request per tracked IPO still being checked (at most 10) and at most 3 cover reads (the first 160 KB of the newest S-1/S-1/A/F-1/F-1/A/424B4/424B1): at most 13 requests, paced like the poll (125 ms). The earnings polls' own requests and pacing are unchanged. Once listed, an IPO is checked only for its own final prospectus (often filed a day or two after the first trade; one filed up to 5 trading days after the first session counts): until one is read completely, or 10 trading days after the first session, then one `ipo-no-final:<slug>` warning and no more checks. Nothing else filed after listing joins the timeline. A cover replaces the page's facts only when it yields everything it must (a final prospectus its price and shares; an amendment every kind the current cover has); otherwise an `ipo-cover-partial` warning names what was missing. D1: one state read, one write per cover read (its attempt, written first), one write with the results, and the kv marker. CPU: a cover read took about 1.7-1.9 ms cold and 0.1 ms warm natively in release; Wasm is a few times slower.
- **`ipo:sweep`** (jobs queue): queued by an earnings poll from 16:30 ET on trading days, one message per IPO not yet swept that day (kv `ipo_sweeps`). One Tavily search and one model call: 2 requests. The search asks for 7 results (`HITS` 5 plus 2 spare; a basic search is 1 credit whatever the count) from the allowlisted hosts only (`include_domains`, built from `OUTLETS`), with the full article text; the outlet check still runs on every result, then a second copy of the same article on the same host (same title, or the same first 300 letters and digits, under another URL) is dropped and the first 5 go to the model. Two outlets with the same headline or the same opening both stay. Known limit: two different articles from one outlet that open with the same long standfirst are merged; the drop is counted in `duplicates`. No model-written sentence is stored: every item shows as its attributed quote. D1: about 7 queries.
- **The last sweep's outcome** is kept per IPO in kv `ipo_sweep_last:<slug>` (JSON): `at`, `slot`, `skipped`, `found` (results returned), `duplicates`, `hits` (articles sent to the model), `proposed`, `kept`, `rejected` (each `Reason url`), `errors`, and `error` for a store error that ended it. Read it with `cd crates/generator && pnpm exec wrangler d1 execute prebell --remote --command "SELECT key, value, updated_at FROM kv WHERE key LIKE 'ipo_sweep_last:%'"`. A sweep that kept nothing shows here whether nothing was found, nothing was proposed, or the checks refused what was. A sweep stops for an IPO 30 days after its first session, after 60 days with no new filing, or once withdrawn.
- **Recap**: with the switch on, the recap's batched Yahoo close read also asks for tracked symbols from `range_set` on, once an `EFFECT` notice or a final prospectus is on file, only while the last 50-symbol batch has room (31 slots with the 519-ticker universe), so no extra request. A tracked symbol that is itself a universe ticker (ANT, since 2026-11-19) is read once, with the universe, takes none of that room, can be a mover like any universe ticker, and its trading row (close, IPO price, change) comes from that same quote; plus 1 D1 read and, with a close, 1 write. Its diagnostics line shows `ipo symbols=N closes=M` (or `ipo_err=...`).
- Logs: `job ipo:check: CheckOutcome { companies, new_filings, covers, rows, throttled, errors }` and `job ipo:sweep: SweepOutcome { slug, slot, skipped, hits, proposed, kept, rejected, errors }`. `rejected` lists each dropped item's reason (`QuoteNotInArticle`, `NotAnOutlet`, `CompanyNotNamed`, `NotTheCompanysValuation`, `NotTheCompanysTradingDate`, `DateNotInQuote`, `NotDirectQuote`, ...) and URL.
- **The news checks**: an item's quote must be word for word in the full article from an allowlisted outlet and name the company. A valuation or an expected date is then kept only when its sentence has one of the allowed shapes (lists in `docs/decisions.md`, 2026-11-11, "accept by template" and "valuations are current"): the company itself valued now (no speculation, projection, difference, condition, question or past-dated figure; "would" only for the offering's pricing), or the company or its shares the subject of a present or future trading verb on that day (no negation, change, condition or question). A listing date may name the company by its ticker instead: a sentence opening "Shares" or "The stock" that gives the symbol stored from the cover (`ipo_watch.symbol`, case-sensitive) as the listing's own, "under the symbol X" or "(Nasdaq: X)", after the date and with no other name there, in an article whose headline names the company; a bare mention ("a day after ANT's debut") does not count (`docs/decisions.md`, 2026-11-11, "filed ticker"); with no symbol stored, it is refused. Word lists (comparisons, other parties, bounds) are a second line. Invisible characters (zero-width, direction marks, soft hyphen and the like) are deleted before the shapes are read; a refusal word they would hide that way ("in<U+200B>May" read as "inMay") still refuses, because the refusal lists are also read with them as spaces.

### The switch

`IPO_WATCH_ENABLED = "true"` in `crates/generator/wrangler.toml` `[vars]`. Only exactly `"true"` is on; unset, `"false"`, `" true"` or `"TRUE"` is off. Off: polls queue no IPO messages (and read nothing for them), a stray `ipo:check` or `ipo:sweep` logs `disabled (IPO_WATCH_ENABLED is not true); skipped`, and the recap reads no IPO symbols. The site keeps showing what is stored, and drops a reported date that has passed by itself (nothing recomputes rows while off). To turn it off, delete the line (or set it to anything else), commit and deploy the generator.

### Alerts

Each at most once a day per key; the IPO keys are per IPO.

- `ipo-cover-failed:<slug>` (error): a cover failed 3 reads (one an hour) and is given up. Look at the filing on EDGAR.
- `ipo-cover-partial:<slug>` (warn): a newer cover was read but lacks what it needs to replace the current facts (it names the filing and the kinds); the page keeps the earlier facts and status. A new cover wording may need a pattern in `cover.rs`; check it against the filing.
- `ipo-cover-empty:<slug>` (warn): a cover read gave no facts at all (an amendment filed only for exhibits is not alerted).
- `ipo-no-final:<slug>` (warn, once ever): the IPO listed but no complete final prospectus was read within 10 trading days; the page shows no IPO price, and checks for it have stopped. Read the 424B4 on EDGAR; a new cover wording may need a pattern.
- `sec-throttled` (error, shared with the earnings poll): SEC answered 403/429 in the IPO check, which then stopped for that hour.
- `ipo-sweep:<slug>` (warn): the news search or the model call failed; the next day tries again.
- `ipo-search-cap` (warn): the month's 30 searches are used.
- `config:ipo:<date>` (error): a store error or a bad LLM or `SEC_CONTACT` config in an IPO job. The hour (check) or the day's slot (sweep) is marked first, so it is not re-queued every 5 minutes.

### Known limits

The list for v1, with the reasons, is in `docs/decisions.md` (2026-11-11, "IPO watch, known limits for v1"). In short:

- News items are kept only in fixed sentence shapes (the lists are in `docs/decisions.md`, "accept by template" and "valuations are current"), so some true reports are dropped. Measured on clean wire sentences: dates 10 of 12, current valuations 8 of 12; the dropped ones are listed in the test `recall_on_clean_wire_sentences`.
- A hedged or conflicting date report in an accepted shape is kept, with its outlet and quote; the newest wins.
- Valuations print as the stored figure without the quote's hedge; the quote is shown beside it.
- No past-dated valuations in v1 ("valued at $965 billion in May" is dropped); a `value_as_of` column would bring them back.
- The model can still propose an in-shape sentence that is not about the company's own figure or date; every item is shown as reported by its outlet, unconfirmed, with its quote.
- Covers like Figma's 424B4 (no share count in the heading) never read completely: such an IPO stays at its range and ends with `ipo-no-final`.
- No opening price after listing (the recap's quote read has none). A new listing's first-day close is stored only if Yahoo's v7 quote gives a previous close for it; if day one has no close, no session is called the first day.
- Items are deduplicated by URL, so an article updated in place keeps its first stored version; the sweeps' monthly counter can be off by one if two sweeps start at the same moment.

## IPO write-ups

A short write-up in English and Chinese each time a tracked IPO's filings prove a step: `filed`, `range_set`, `range_changed`, `priced`, `listed`, `withdrawn`. An ordinary post (`content_type = 'ipo'`) in the recent list and the archive, linked from the IPO page. **Written entirely by code** from stored filing facts (sentence templates per milestone and language): no model call. Design `docs/superpowers/specs/2026-11-11-ipo-articles-design.md`; what the site reads, `docs/superpowers/specs/2026-11-11-ipo-articles-contract.md`; the rules, `docs/decisions.md` (2026-11-11, the "IPO write-ups" entries). Code: `crates/core/src/ipo/milestone.rs` (what proves a step, the facts bundle), `writeup.rs` (the templates, the page and its guard), `article.rs` (the message).

### What runs, and when

- **`ipo:article`** (earnings-build queue, serial with the earnings builds): queued by an earnings poll, 06:00-22:00 ET on trading days, once kv `ipo_article_next` is reached (an hour after an idle pass; at a failed build's retry time). One D1 state read, then per tracked IPO its latest milestone and its run (`runs.run_key` = `ipo:<slug>:<milestone>:<key>`). At most one build per message: two R2 writes (the facts object and the cover graphic `covers/<post slug>.svg`) and about 10 D1 queries. No model, EDGAR, Yahoo or Tavily request.
- **Cover and share card**: the build draws the milestone's cover graphic from the facts (see "Cover graphics") and stores it before the post row, so the write-up goes live with its `cover_key`; a `withdrawn` write-up, a milestone missing a figure, or a failed R2 write publishes without one (flat tile, default card) and never fails the build. A write-up that went live with a cover queues a `cards` message, so its share card `og/<post slug>.png` is rendered in a message of its own (never in the build's invocation, for the 10 ms CPU limit) within about a minute; the log line ends `; card queued`.
- **Cover backfill**: a message that built nothing gives at most one already-published write-up without a cover its cover, recomputed from its stored facts bundle (`facts_r2_key`), and queues its card. Only write-ups whose filing or session is at most 14 days old (older ones would get no card), not `withdrawn`, with the English text live. Each try is counted first in `covers/<post slug>.attempts` (R2, never served); after 3 tries it is given up, and facts that give no graphic use up all 3 at once. Setting `cover_key` (keeping `published_at` and `revised_at`) makes it once only. Cost of every idle pass: one D1 read per reached, non-`withdrawn` milestone of each tracked IPO in the 14-day window, whether or not a post exists for it; a coverless write-up whose 3 tries are used up adds one R2 read (its `.attempts` counter, read before anything else) on every pass until it is 14 days old. A pass that tries a cover adds one D1 read (the English translation), two R2 reads (the counter and the facts), two R2 writes (the counter and the SVG) and one D1 write. Because the post keeps its old `published_at`, the `cards` scan (the 30 newest cover posts by `COALESCE(revised_at, published_at)`) may not reach it when more than 30 newer cover posts sit in the 14-day window; it then keeps the default card, which is safe (on 2026-11-12 there were 3 newer cover posts, so the Anthropic write-up is well inside). Log: `cover added: covers/<slug>.svg`, or `no cover: <why>`. This is how the first live write-up (`anthropic-ipo-price-range-2026-11-10`, published with `cover_key` NULL before IPO covers existed) gets its cover and card: on the first idle `ipo:article` pass after deploy, no SQL by hand. To retry a given-up cover, delete its `.attempts` object: `cd crates/generator && pnpm exec wrangler r2 object delete prebell-facts/covers/<slug>.attempts --remote`.
- **Once only**: a run that is `published`, `skipped` or `failed` is never built again. Only the latest milestone an IPO has reached is written; one it has moved past is never written later. A range or a price counts only from a cover that became the IPO page's facts source, so a write-up never disagrees with the page.
- **`listed` waits for the confirmed first day**: it is written only once `ipo_watch.date_source = 'trading'` (the stored session is the filings' first trading day). Until then the pass logs `waiting for the first trading day to be confirmed`; never confirmed within 7 days, it is skipped with a warning.
- **Never in one language only**: both pages are rendered and checked; then the post row, and both translations with the sources in one D1 batch.
- **The guard**: every number and date on the page outside the quoted news must be one the facts hold (`writeup::verify_page`). A page that fails is a template bug: nothing is published and the run is retried and then failed as below.
- **Retries are bounded**: a build that fails (a D1 or R2 error, or the guard) is tried again after 5, 15, 30 and 60 minutes (a build that dies mid-way holds its 15-minute lease first); the fifth failed build marks the run `failed` with an error alert. So a milestone costs at most 5 builds, over about two hours.
- **The first live run**: Anthropic's `range_set` (the S-1/A of 2026-11-10, run key `ipo:anthropic:range_set:0001628280-26-072484`, slug `anthropic-ipo-price-range-2026-11-10`) at the first poll after deploy, with no news items stored yet. A test renders it from the real cover facts.
- CPU: a build is template formatting and the guard's number check (the same checker the earnings write-ups use); no model wait.

See a write-up's state: `cd crates/generator && pnpm exec wrangler d1 execute prebell --remote --command "SELECT run_key, status, attempts, last_error, updated_at FROM runs WHERE content_type = 'ipo' ORDER BY updated_at DESC"`; the next pass: `SELECT value FROM kv WHERE key = 'ipo_article_next'`.

### The switch

`IPO_ARTICLES_ENABLED = "true"` in `crates/generator/wrangler.toml` `[vars]`, on (Rick, 2026-11-11). Only exactly `"true"` is on, and only while `IPO_WATCH_ENABLED` is on too. Off: polls queue no `ipo:article` (and read nothing for it), a stray message logs `disabled (...); skipped`; published write-ups stay. To turn it off, delete the line, commit and deploy the generator.

### Alerts

- `<run_key>` (warn): the milestone was first found more than 7 ET days after its filing or session, or a `listed` session was never confirmed as the first day; skipped, never published late.
- `<run_key>:<ET date>` (warn, once a day): a build failed and will be retried (`runs.last_error` says why: a store error, or the guard's numbers or dates).
- `<run_key>` (error): the fifth build failed; the run is `failed`. A guard failure means a template printed something the facts do not hold: fix the template.
- `config:ipo:<date>` (error, shared with IPO watch): a store error that ended the message.

### Costs

No model calls and no Tavily searches. Per milestone: one queue message with one R2 write and about 10 D1 queries, five at the most when builds fail. About five milestones an IPO.

### Preview and deploy

Local preview: after `db/seed-ipo-preview.sql`, `cd crates/generator && pnpm exec wrangler d1 execute prebell --local --file ../../db/seed-ipo-articles-preview.sql`, then `bash db/load-preview-facts.sh` for the facts object. The filing facts are real and the text is the generator's own rendering; the quoted items are the made-up ones of the IPO seed. No migration. Deploy is the generator's usual `pnpm exec wrangler deploy` (owner only) with the site's support for `content_type = 'ipo'`.

### Known limits

- A step the stored data does not prove gets no write-up: a cover that could not be read completely, a 424B4 read only after the first session (no `priced` write-up then; the `listed` one states the price if the 424B4 is the facts source by then), or a listing whose first day Yahoo did not give.
- If day one's session is missed and no `priced` write-up was published, that IPO gets neither a `priced` nor a `listed` write-up: `listed` waits for the confirmed first day, then is skipped with an alert after 7 days.
- The text says only what the covers and the first session state. Nothing about the business, the market, demand or valuation appears except in the quoted news.
- "The first registration statement to state a price range" is said only when every earlier registration statement was read (not for Anthropic, whose S-1 and first S-1/A were never read).
- Quotes are as stored by the news sweep; in Chinese they stay in English. Outlet names stay as stored.

## Mover insights

A hook and one "watch next" sentence per big mover, in English and Chinese: written by Claude from an evidence pack, checked by code, then by a strict judge (spec: `docs/superpowers/specs/2026-11-13-mover-insights-design.md`, Plan 2: `docs/superpowers/plans/2026-11-17-mover-insights-shadow.md`). The shadow stage stores every line and verdict in R2; readers see nothing.

### The switch

`INSIGHTS_MODE` in `crates/generator/wrangler.toml` `[vars]`: `"off"` (unset is the same) or `"shadow"`. Since 2026-11-17 it is `"shadow"`, on Rick's go; the first run was capped at 10 calls, and since 2026-11-18 `INSIGHT_MONTHLY_CALLS = "300"` (`docs/decisions.md`, 2026-11-17 and 2026-11-18). Off means nothing runs: no insight message is queued by a publish or a cron, a stray one returns before any read, and no model is called. Any other value is a config error, alerted once per ET day under `config:insight:<date>`; it still queues one insight message per firing in the sweep windows, so the error is reported. Turning it to `shadow` was Rick's call (2026-11-17, after the dry run of writer v6 and judge v3, Plan 2, Task 7). The first shadow run was the CPU measurement on Workers (below), capped at 10 calls; Rick raised the cap to 300 on 2026-11-18.

### Before the first deploy that includes it (owner only)

Create the queue first, as its own step, with the owner's go: `cd crates/generator && pnpm exec wrangler queues create prebell-insight`. Then deploy, so the deploy creates nothing. If the queue is missing, the deploy does not fail; it creates the queue by itself: in wrangler 4.154.0, the version this repo's lockfile pins, `wrangler deploy` provisions bindings by default (`--x-provision` defaults to true), so it skips its pre-upload queue check and creates `prebell-insight` with no prompt (read from wrangler 4.154.0's source, `wrangler-dist/cli.js`; not observed on a deploy). To have a deploy refuse instead, deploy with `--x-provision=false`: it then stops before uploading with "Queue \"prebell-insight\" does not exist" (from the same reading of the source). The queue has one consumer, one message per batch and one at a time, so a writer or judge call never runs beside the briefs and two insight messages never run at once. Queues on the Workers Free plan: 10,000 operations a day across all queues (a delivered message is 3: write, read, delete), per https://developers.cloudflare.com/queues/platform/pricing/; shadow adds about 50 messages a trading day, about 150 operations.

### What runs, and when

After a brief, its 8:35 update or a recap publishes, its job queues an `insight` message; the crons queue one sweep message per firing at 08:10-09:30 and 16:10-17:30 ET on trading days. Each bundle's record goes write (the writer's reply stored as `replied`), check (`written`), judge (the judge's reply stored as `judged`, then `done`), each its own message, so a CPU kill never makes a paid call be paid again. When the code checks refuse a written line, the record goes `refused` instead: one rewrite call for the refused lines only (`insight-rewrite/v1`: the writer's own rules, then each refused line with its evidence pack and the exact check failures; it may also leave a mover out), its reply stored as `rewritten`, then the same code checks on its lines in their own message; lines that now pass go to the judge with the writer's, and lines that still fail stay refused with both check results. Judge refusals are never rewritten. At most one rewrite try per bundle: a try killed mid-call is not made again, a failed call is not retried, and with fewer than two calls left under the month's cap (the rewrite and the judge after it) it is not made; in each case the lines stay refused and the record goes on. A bundle with a refusal takes up to five messages instead of three. A sweep leaves a record another message wrote in the last 5 minutes alone. Records of today and the previous trading day are picked up, so Friday's are finished on Monday.

### Cost and the cap

At most `INSIGHT_MONTHLY_CALLS` model calls per ET month (default 300: $2.40 to $6 a month at the trial's measured $0.008 to $0.02 a call), each claimed in kv `insight_calls:<YYYY-MM>` before it is made, the rewrite's included. A bundle normally makes 2 calls (writer, judge), or 3 with a rewrite; the worst case is 7 (3 writer tries, the rewrite, 3 judge tries). At 3 bundles a trading day and about 21 trading days, that is about 189 calls a month even if every bundle had a rewrite, under the 300; at the cap the step stops for the month and says so once in the log. Read the count: `pnpm exec wrangler d1 execute prebell --remote --json --command "SELECT key, value FROM kv WHERE key LIKE 'insight_calls:%'"`. Writer and judge are `claude-sonnet-5-5`, effort low (`INSIGHT_WRITER_PROVIDER`, `INSIGHT_JUDGE_PROVIDER`; never `LLM_PROVIDER`), with the `ANTHROPIC_API_KEY` secret; without it the step logs and skips.

### The first measurement on Workers (2026-11-17)

Before the first run the step's cold CPU was known only from V8 under Node (`tools/insight-cpu-wasm`), where the check step took about twice a share card render's first call, and the docs did not settle how much CPU a free-plan queue consumer gets. The first shadow run (generator version `fdc640a3`, `INSIGHT_MONTHLY_CALLS = "10"`, read with `wrangler tail --format json`) settled it for this step:

- Five bundles finished within six minutes; every invocation's outcome was `ok`.
- CPU per `insight` invocation: 174 ms for the first write step and 129 ms for the first check step (cold), then 13 to 27 ms; one idle sweep at 22 ms. The earnings poll ran at 84, 141 and 179 ms in the same capture, and earnings builds on the morning of 2026-11-18 completed at 159 to 326 ms, so invocations of this size complete on the free plan. No limit was read from the platform; this is what completed.
- At most 14 subrequests in one `insight` invocation (`insight_ops` 13 plus `subrequests` 1, the judge step), and at most 5 D1 queries; 17 counting both.
- The rewrite (2026-11-19, not yet measured on Workers): the rewrite message is at most 18 subrequests by the code's count (the judge message is 20 and the write message 28, so the worst case is unchanged), with 3 D1 queries and one model call, and compiles no pattern (a fresh-process test checks it): its CPU is the record's JSON read and written, as in the judge message before its call. The recheck message is the check step's work over the refused lines only (at most 15 subrequests), with the same 22 patterns compiled cold, so its cold CPU should be at or below the check step's 129 ms. Both are derived from the code and native tests, not measured on Workers: capture `wrangler tail` after the deploy and read `cpuTime` and `outcome` on a bundle with a refusal.
- The check step is not split by language for now. That rests on one cold check sample (129 ms) and on heavier jobs completing beside it, not on a known limit: measure again if any `insight` invocation ends with an outcome other than `ok`.

Not exercised by that run: the stop at the cap (the count matched the records, 4 calls, but the cap was not reached). To measure again, capture `wrangler tail prebell-generator --format json` across a sweep window (08:10-09:30 or 16:10-17:30 ET) and read `cpuTime` and `outcome` per event.

### Records

One per facts bundle, in the `prebell-facts` bucket: `insights/premarket/<date>.json` (the 8:00 brief), `insights/premarket/<date>-update.json` (the 8:35 update), `insights/recap/<date>.json`, beside `insights/<...>.attempts` (write tries and when). Read one: `cd crates/generator && pnpm exec wrangler r2 object get prebell-facts/insights/recap/2026-11-18.json --remote --file /tmp/insight.json`. Its `stage` (`replied`, `refused`, `rewritten`, `written`, `judged`, `done`), per mover its `pack`, `insight`, `check` (the code checks' refusals), `verdict`, `judge_error` and `passed`, and the raw `writer_reply` and `judge_reply`. After a rewrite, a mover the rewrite answered for holds the rewrite's line in `insight` and its refusals in `check`, and the writer's line and its refusals in `rewritten_from`; a refused mover the rewrite gave no line has `rewrite_error` (left out, call failed, not made). The record then also has `rewrite_version`, `rewrite_model`, `rewrite_attempts` and the raw `rewrite_reply`. `skipped_reason` is "the writer wrote no line" when the writer wrote none, and "no line passed the code checks" when lines were written (and rewritten) but none passed.

### The review page

From the repository root: `tools/insight-trial/fetch-shadow.sh <first shadow day> "$(date +%F)" tools/insight-trial/shadow` (read-only), then in `tools/insight-trial`: `env -u CARGO_TARGET_DIR cargo run --release -- shadow --records shadow --out out-shadow --labels <labels.json>` writes `out-shadow/label.html` (every line the judge answered for, labelled ones shown done), and `… -- score --out out-shadow --labels <labels.json>` reports the bar (50 judge-passed lines read, none wrong). See `tools/insight-trial/README.md`.

### Switching it off

Set `INSIGHTS_MODE = "off"` (or delete the line) and deploy. Messages already queued then return without reading anything; stored records stay in R2.

## Logos

Company logos (the white tag on earnings-check covers and the company cards on the earnings calendar) and partner logos are static files in `apps/web/public/logos/`, served as Workers static assets. Pages never fetch a logo from a third party. `apps/web/scripts/build-logos.mjs` (`pnpm logos` in `apps/web`) builds every file, the manifest `apps/web/src/lib/logos.generated.ts` (`COMPANY_LOGOS` ticker -> path with a `?v=` content hash, because `/logos/*` is served immutable for a year; `PARTNER_LOGOS` the same for partner marks; `COMPANY_LOGO_SIZES` ticker -> natural CSS size; read through `companyLogo()` and `companyLogoInfo()` in `src/lib/logos.ts`) and `apps/web/public/logos/LICENSES.md`. Never edit those by hand. It covers every row of `watchlist.tsv` (both tiers), so a rerun picks up new rows. Cards are wide, so a horizontal wordmark is preferred. For each ticker the script takes the first of:

1. **Wikimedia Commons via Wikidata:** the company's Wikidata item is found by the SEC CIK in `watchlist.tsv` (or `WIKIDATA` in the script) and its P154 "logo" is used. `COMMONS` in the script names a file to use instead (the Wikidata one is wrong or the wrong shape); `NO_COMMONS` drops Commons for a ticker (wrong company, a subsidiary, a product or an old brand). Only files Commons lists as public domain or CC0 are used (CC BY and CC BY-SA need a visible credit, which no page gives). A logo wider than 6.5:1, a raster wordmark under 120px wide or any other raster under 64px is not used; one up to 9:1 is used only as a last resort.
2. **`COMMONS_FALLBACK`**, then **Simple Icons** (`COMPANIES`): a CC0 glyph from the pinned `simple-icons` devDependency, for symbol-only marks.
3. **Wikidata's P8972 "small logo"**, then a **Commons search** for the company name (the file name must hold the whole core name and "logo"; review every one of these), then
4. **the company's own site icon**, last resort: the largest `apple-touch-icon` / `icon` / `favicon.ico` image of at least 64px linked from the homepage (the domains in `watchlist.tsv`, then Wikidata's P856). `NO_SITE_ICON` stops this for a ticker whose site icon is wrong.

Company files are 2x PNGs (a few are SVG glyphs): a wordmark is trimmed and fitted inside 128x48 CSS px with no tile, so the card's own background shows; a full-bleed app icon is a rounded square; a mark too pale for white is set on a dark pill. `SKIP` keeps a ticker as a text chip on purpose. Partner marks (`PARTNERS`) are square tiles from simple-icons or the partner's own site.

- **Run it:** downloads go out at most two a second to Wikimedia and one a second elsewhere, with the User-Agent `PreBell logo build (https://prebell.site; support@prebell.site)`. Definitive answers (2xx, and 4xx other than 408/429) are cached in `apps/web/node_modules/.cache/logos`, so a rerun gives the same files; `pnpm logos --offline` uses only the cache. Delete the cache to fetch everything again (a full run takes about 30 minutes; one that stops, say on a Wikimedia timeout, resumes from the cache on the next run). The script prints each source's tickers, the ones left without a logo and why each candidate lost. Before committing, review every new or changed logo on a 150x72 white card and on the 18px cover tag; Commons search results and site icons need the closest look.
- **When it fails:** the script builds in `apps/web/node_modules/.cache/logos-build` and moves the result into `public/logos/` and `src/lib/logos.generated.ts` only when the whole run succeeds. A failed run leaves the committed files as they were. It stops with an error when Wikidata, Commons or a partner file doesn't answer (a timeout, 429 or 5xx is never cached, so just run it again later). It also stops when a ticker that has a logo in the committed manifest would lose it; pass `--allow-shrink` only if that is intended. Company sites that fail the same way are reported at the end and retried on the next run.
- **Browser caching:** `apps/web/public/_headers` serves `/logos/*` with a one-year `immutable` Cache-Control, so a tile replaced under the same file name may keep showing the old image to returning visitors for up to a year.
- **Add or fix a company logo:** if Simple Icons has the brand, add `TICKER: "slug"` to `COMPANIES`. Otherwise, if Wikidata picks a wordmark that is too wide, find the company's own square mark on Commons and add `TICKER: "File name.svg"` to `COMMONS` (the licence check still applies). If the result is unreadable at 18px, add the ticker to `SKIP` with the reason. Use only the company's own current mark.
- **Refresh all logos:** bump `simple-icons` (exact version) in `apps/web/package.json`, set `FETCHED` in the script to that day, delete the cache and run `pnpm logos`. If a brand was removed upstream (usually because the brand asked), the script stops with `simple-icons X has no "slug"`. Remove that ticker from `COMPANIES` too.
- **Partner logos:** set `url` (the partner's own file) and `page` (where it is linked) in `PARTNERS`, run `pnpm logos`, then set `logo` on the partner in `apps/web/src/lib/partners.ts`. The partner strip shows names only, so a logo is kept on disk and in the `/api/partners` response but not drawn; `logoDark` is optional.
- Without a logo, a cover's tag shows the ticker as text. Nothing breaks if a file is missing; the tests check that every manifest entry exists, and that every file has a `LICENSES.md` row.
